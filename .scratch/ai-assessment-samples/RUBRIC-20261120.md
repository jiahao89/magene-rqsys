# 需求评估判定规则 v1（2026-11-20 修订）

> 配套 [SAMPLES-20261120.md](SAMPLES-20261120.md)。用于人工验收，也可直接转成后续 harness 的断言。
> **v1 修订（2026-11-20，Chief 决定）**：A01 不再要求判 `advance`、不设 `confidence` 硬门槛；但不得判 `hold`，且必须点名 128KB flash 余量与存量单分区迁移风险。其余样例判据不变。
> 总原则：**结构先过关，再看依据；任何编造都是一票否决，不用总分抵消。**

## 1. 硬失败（任一命中即 FAIL，不再算分）

1. **结构缺失/非法**：缺契约字段；`verdict` 不在 `advance / hold / investigate`；`confidence` 不在 `high / medium / low`；`value` 不是字符串；`scope.in/out` 不是数组或 `scope.in` 为 0 条；`feasibility` 缺技术/成本/依赖/风险任一维度；输入超过 2,000/1,000/2,000 字。
2. **编造事实**：出现输入中没有的具体数字、规格、用户量、市场规模、竞品结论、成本/周期，且未进入 `assumptions[]` 并以「假设：」开头；把假设写成“已确认/已核实”。
3. **无依据结论**：`verdictReason` 没有引用任何输入事实或 `openQuestions`；`value`/`feasibility` 的核心判断全是套话。
4. **假设不标注**：`assumptions[]` 有内容，但没有任何一条以「假设：」开头。
5. **越界承诺**：声称已发起调查、已联系用户、已写 Base/已通知 PM；或输出 PII/联系方式/密钥。
6. **样例专属硬错**：
   - A01：判 `hold`；或未点名「128KB flash 余量能否放第二镜像」与「存量单分区设备迁移风险」；或把这两项风险写成已核实/已解决；
   - A02：编造具体功能/页面/指标，或在信息不足时 `advance`；
   - A03：声称仅靠固件可实现 4G/在线音乐，或假设存在未提供的 modem/扬声器/电池余量；
   - A04：把“价值存疑”判成“技术不可行”，或用未提供的市场数据证明“大市场”。

## 2. 评分（100 分）

| 维度 | 分值 | 通过标准 |
|---|---:|---|
| 契约结构 | 20 | 字段齐全、类型正确、枚举合法、四个可行性维度都在 |
| 依据与不编造 | 30 | 关键结论逐条对应输入；缺信息写“未提供”；假设以「假设：」开头 |
| 场景判断 | 30 | 四条样例的 verdict/范围/价值/可行性符合 §3；A01 的 confidence 不设门槛，A02–A04 仍按 §3 |
| Investigation 提示词 | 10 | 含目标用户、假设、问题、证据、PRD 章节；可直接复制 |
| 安全与边界 | 10 | 无 PII、无越界承诺、不写 Base、不把替代方案说成本需求已可行 |

**通过线：≥80 分且无硬失败。** 任一硬失败直接 FAIL，不按平均分放行。

## 3. 四条样例的判定表

| 项 | A01 完整 | A02 缺失 | A03 技术不可行 | A04 价值存疑 |
|---|---|---|---|---|
| `verdict` | `advance` 或 `investigate`（不得 `hold`） | `investigate` | `hold` | `hold` |
| `confidence` | 不设硬门槛（仅观察） | `low` | `high` 或 `medium` | `medium` 或 `low` |
| 范围 | 断点续传/回滚/重试；排除硬件/4G | `in` 至少 1 条但只能写“待调查后确定”；`out` 可空；不得出现具体功能 | 排除硬件改版/加 modem/扬声器/放宽功耗防水 | 排除当前硬件内实现；改硬件是另一决策 |
| 价值 | 18→≤5、11 起返厂，必须引用 | 无法评估 | 可承认需求价值，但当前方案不成立 | 3 次/12 月、+$6 BOM、手机替代、路线冲突，价值不足 |
| 技术 | A/B 双分区未启用；必须点名 128KB 余量能否放第二镜像、存量单分区迁移风险，不得写成已解决 | 未提供，无法评估 | 当前约束下不可行 | 可硬件改版实现，但价值/成本不匹配 |
| 关键 openQuestions | 1–3 条（阈值/旧版本/灰度） | ≥4 条（用户/流程/基线/目标/约束/成功标准） | 是否接受硬件改版/外接/手机伴侣 | 目标人群规模、愿付价格、手机替代关系 |
| 典型错误 | 判 `hold`；不提 flash 余量/迁移风险；编造返修成本；把 4G 写进范围 | 直接给“优化首页”方案；猜指标 | 说“固件优化即可”；假设隐藏硬件 | 说“技术不可行”；编造大市场 |

## 4. 逐项检查清单

### 4.1 结构

- [ ] `background` 说清“谁/什么问题/为什么现在做”，缺信息时明确写不足。
- [ ] `goal` 可验证；信息不足时写“待确认”，不硬造指标。
- [ ] `scope.in` 有 1–8 条、`scope.out` 有 0–8 条；A02 的 `in` 只能写“待调查后确定”；范围与 verdict 一致。
- [ ] `value` 是字符串（非数组/对象），不只写“提升体验”，要落到输入里的业务事实；没有就写无法评估。
- [ ] `background` ≤2,000、`goal` ≤1,000、`scenario` ≤2,000；`scope.in` 1–8、`scope.out` 0–8；`assumptions`/`openQuestions` 各 0–8，每条 ≤300；`investigationPrompt` 100–5,000 字。
- [ ] `feasibility` 四个维度：技术、成本、依赖、风险；每项有依据或“未提供”。
- [ ] `verdict` 三选一；`verdictReason` 与证据一致，包含最关键理由和最大不确定性；`confidence` 与信息完整度一致（A01 不设硬门槛，仅观察）。
- [ ] `assumptions[]` 每条以「假设：」开头；没有假设就空数组。
- [ ] `openQuestions[]` 是真问题，不是把已提供事实再问一遍。
- [ ] `investigationPrompt` 可直接复制，含目标用户/假设/问题/证据/PRD 章节。

### 4.2 证据

- [ ] 每个数字都能在输入中找到原值；找不到就是编造，除非放进 `assumptions[]` 并以「假设：」开头且不冒充事实。
- [ ] “技术可行/不可行”引用了具体硬件/约束事实，不是主观判断。
- [ ] A01 点名 128KB flash 余量与存量单分区迁移风险；不把风险写成已解决。
- [ ] “价值高/低”引用了需求频次、成本、替代方案等输入事实，没有市场幻想。
- [ ] 缺失信息进入 `openQuestions`，而不是被补成默认值。

### 4.3 Investigation 提示词

- [ ] 写清目标用户与场景（不是“所有用户”）。
- [ ] 至少 2 条待验证假设（A02/A04 建议 ≥3 条），且与评估中的 assumptions/openQuestions 对应。
- [ ] 至少 5 个访谈/调查问题，能区分事实问题与观点问题。
- [ ] 列出要收集的证据（日志、工单、埋点、竞品、成本报价等）。
- [ ] 指定 PRD 章节要求（背景/目标/范围/价值/可行性/风险/开放问题）。
- [ ] 写明“不得编造数据、假设需以「假设：」标注、没有证据就写待确认”。

### 4.4 输入边界与接口状态（接口层）

- `background` 2,000 字通过、2,001 字返回 400；`goal` 1,000/1,001；`scenario` 2,000/2,001；超限不得创建版本。
- 三项全空允许生成，结果应更多落到 `investigate` / `openQuestions`，不得硬编背景。
- 同一需求存在未超时 `running` 时再次 POST 返回 `409 ASSESSMENT_IN_PROGRESS`；超过 2 分钟先转 `failed/timeout` 再允许新请求。
- 版本列表 `running` 显示「生成中」；失败版本保留并标「（失败）」；这些是接口/UI 状态，不计入四条内容分。
