# AI 需求评估样例集 v0（2026-11-20）

> 用途：验证「需求评估」按需生成能力。四条样例分别覆盖 **信息完整 / 信息严重缺失 / 技术不可行 / 价值存疑**，全部为虚构场景，不含真实客户、订单或联系方式。
>
> 契约依据：2026-11-20 最终契约（`background / goal / scope.in[] / scope.out[] / value / feasibility / verdict / verdictReason / confidence / assumptions[] / openQuestions[] / investigationPrompt`）。本文件只定义输入和预期行为，不新增接口字段。

## 0. 总表

| ID | 场景 | 补充信息 | 预期 verdict | 可接受 confidence | 核心考点 |
|---|---|---|---|---|---|
| A01 | OTA 弱网断点续传与回滚 | 背景、目标、场景、硬件约束齐全 | `advance` | `high` | 信息完整时能给出可执行结论，范围/可行性/价值都有依据 |
| A02 | “App 不好用，优化一下” | 只有一句转述，无目标/场景/数据 | `investigate` | `low` | 缺信息时不硬编需求、不猜数字，先列调查问题 |
| A03 | C606 增加 4G + 在线音乐，且不改硬件 | 硬件事实明确：无 modem/扬声器、功耗受限 | `hold` | `high` / `medium` | 技术不可行要顶住，不能把“加硬件”说成固件能解决 |
| A04 | C606 增加 FM 收音机 | 需求少、成本/防水代价明确、手机可替代 | `hold` | `medium` / `low` | 技术可行但价值存疑，不能误判为技术不可行或夸大市场 |

## 1. 通用判定（四条都适用）

### 1.1 结构

- 必须返回最终契约的全部字段；`verdict` 只能是 `advance` / `hold` / `investigate` 之一；`confidence` 只能是 `high` / `medium` / `low` 之一。
- `scope.in[]` / `scope.out[]` 必须是数组；`feasibility` 必须覆盖技术、成本、依赖、风险四个维度（可以是“未提供/无法评估”，但不能省略）。
- `assumptions[]` 每条都必须以「假设：」开头，写清假设内容和影响哪个判断；不得把假设写成已确认事实。
- `value` 必须是**字符串**（不能是数组/对象），写受益者和依据；`background` / `goal` / `scope` / `value` / `feasibility` / `verdictReason` 均不得为空。
- 输入上限：`background` ≤2,000 字、`goal` ≤1,000 字、`scenario` ≤2,000 字；三项都可为空。`scope.in` 1–8 条、`scope.out` 0–8 条、`assumptions` / `openQuestions` 各 0–8 条，每条 ≤300 字；`investigationPrompt` 100–5,000 字。
- `investigationPrompt` 必须是一段可直接复制走的提示词，不能只是“建议进一步调查”。

### 1.2 依据与禁止项

- `verdictReason`、`value`、`feasibility` 的关键判断必须能对应到输入中的事实；输入没有的数字、规格、用户量、市场规模、竞品结论，一律不得出现。
- 无法判断的项写“未提供/无法评估”，并放进 `openQuestions`；不得用“通常/一般来说”补成事实。
- 不得把“需要改硬件”写成“固件可以解决”，也不得把“价值不足”写成“技术不可行”。
- 不得输出真实 PII、联系方式、密钥；不得声称已经发起调查、已经联系用户或已经写入 Base。

### 1.3 Investigation 提示词必备元素

至少包含：目标用户/使用场景、待验证假设、要问的问题、要收集的证据、PRD 章节要求；并写明“不得编造数据、假设需以「假设：」标注”。缺少两项以上判为不合格。

## 2. 样例

### A01 信息完整｜OTA 弱网断点续传与失败回滚

**需求原文**

- 标题：`C606 码表 OTA 升级弱网断点续传与失败回滚`
- 描述：`售后反馈：骑行途中用手机热点给 C606 升级固件，进隧道断网后升级失败，码表停在升级界面无法开机；希望支持断点续传，失败后能回到旧版本并重试。`
- 来源渠道：售后；型号：C606

**补充输入**

- 背景：`2026 Q3 售后记录 18 起 OTA 失败，其中 11 起返厂；多数发生在山区/隧道，用户用手机热点。当前 OTA 是单分区整包下载，失败后只能返厂重刷。`
- 目标：`下一季度把 OTA 失败从 18 起降到 5 起以下；失败时自动回滚到上一版，用户可重试，不返厂。`
- 场景：`C606 户外骑行，手机热点信号断续；升级时电量在 20% 以上；用户不熟悉刷机。`
- 已知约束（写在背景里）：`不改硬件；bootloader 已有 A/B 双分区但未启用；flash 余量 128KB；OTA 服务端可配合；目标 Q2 前完成。`

**预期结论**

- `verdict = advance`，`confidence = high`。
- `scope.in` 应包含：断点续传/分片校验、失败自动回滚、用户可重试；`scope.out` 应排除：4G/蜂窝硬件、整机硬件改版、返厂流程重做。
- `value` 必须引用 `18 起 → 5 起以下`、`11 起返厂`，不能自行折算金额或编造用户量。
- `feasibility.technical` 必须引用 `A/B 双分区未启用`、`flash 余量 128KB`；`feasibility` 其余维度要提到 OTA 服务端/签名、QA 测试矩阵、断电/回滚风险。
- `openQuestions` 控制在 1–3 条，例如回滚触发阈值、保留几个旧版本、灰度范围；不能把已提供的事实又当成未知。
- `investigationPrompt` 至少覆盖：售后失败样本与日志、固件分区/引导、QA 弱网/断电测试矩阵、支持流程；用于后续 PRD。

**不得出现**

- 编造返修成本、用户规模、竞品 OTA 指标；
- 把 4G/硬件改版写进本期范围；
- 把“A/B 双分区未启用”说成“当前已支持无缝回滚”。

### A02 信息严重缺失｜“App 用起来不顺手，优化一下”

**需求原文**

- 标题：`App 体验优化`
- 描述：`用户说 App 不好用，让优化一下。`
- 来源渠道：运营/用研

**补充输入**

- 背景：`领导转述，具体哪里不好用没说；没有用户原声、截图、埋点或客服记录。`
- 目标：（空）
- 场景：（空）

**预期结论**

- `verdict = investigate`，`confidence = low`。
- `background` 必须明确写“现有信息不足以判断问题与范围”；`goal` 写“待确认”；`value` 和 `feasibility` 各维度写“无法评估/未提供”，不能给具体功能或数字。
- `scope.in[]` 必须至少 1 条，但只能写“待调查后确定”这类范围占位；`scope.out[]` 可以为空；不得出现“优化首页加载”“重做导航”等具体方案。
- `assumptions` 应为空，或最多一条且必须以「假设：」开头；不得把“用户觉得慢”之类未提供的判断写成事实。
- `openQuestions` 至少 4 条：哪类用户/哪个流程、当前基线指标、期望改善、业务目标、时间/人力约束、成功标准。
- `investigationPrompt` 应以发现问题为主：用户访谈、客服/埋点证据、任务走查、基线指标；不能直接要求 PRD 给出功能方案。

**不得出现**

- 编造具体页面、功能、性能数字、用户比例；
- 在信息不足时给出 `advance`；
- 把“领导转述”当成用户原话或已确认需求。

### A03 技术不可行｜C606 增加 4G + 在线音乐，且不改硬件

**需求原文**

- 标题：`C606 增加 4G 独立联网与在线音乐`
- 描述：`希望码表不依赖手机，自己插 SIM 卡上网，并能在线听音乐；不改硬件、不改外壳、不增加功耗。`
- 来源渠道：销售；型号：C606

**补充输入**

- 背景：`销售希望对标竞品。C606 现有硬件只有 BLE 5.0，没有蜂窝 modem、没有扬声器；整机 IPX7 密封；电池 600mAh；当前功耗预算已接近上限。`
- 目标：`骑行时独立联网、在线听歌。`
- 场景：`长途骑行，手机可能没电。`

**预期结论**

- `verdict = hold`，`confidence = high` 或 `medium`。
- `feasibility.technical` 必须明确：在“不改硬件/外壳/功耗”约束下不可行，依据是 `无蜂窝 modem`、`无扬声器`、`IPX7 密封`、`600mAh/功耗接近上限`；不能只说“有难度”。
- `scope.out` 应包含：硬件改版、增加 modem/扬声器/天线、放宽功耗/防水约束；`openQuestions` 至少问“是否接受硬件改版/外接设备/手机伴侣方案”。
- `verdictReason` 必须区分“当前约束下不可行”与“永远不可能”；可以给替代路径，但必须标注是替代方案，不是本需求已可行。
- `investigationPrompt` 应覆盖硬件/功耗/认证可行性、替代方案、用户对手机依赖的容忍度；不能直接让 PRD 按“固件实现 4G”展开。

**不得出现**

- 声称仅靠固件就能支持 4G/在线音乐；
- 假设存在未提供的隐藏 modem、扬声器或电池余量；
- 编造续航、成本、认证周期数字；
- 因为“技术不可行”就否定用户的长途联网需求本身（应区分需求价值与当前方案可行性）。

### A04 价值存疑｜C606 增加 FM 收音机

**需求原文**

- 标题：`C606 增加 FM 收音机`
- 描述：`骑行时想听广播，希望码表内置 FM 收音机。`
- 来源渠道：终端用户；型号：C606

**补充输入**

- 背景：`过去 12 个月收到 3 次相关请求；现有用户以训练/导航为主；产品路线已明确 2026–2027 聚焦训练/导航，不做娱乐硬件；加 FM 芯片和扬声器约增加 6 美元 BOM，需要改外壳并重新做防水；手机已可听广播/音乐。`
- 目标：`增加骑行娱乐功能，提升活跃。`
- 场景：`休闲骑、通勤。`

**预期结论**

- `verdict = hold`，`confidence = medium` 或 `low`。
- `value` 必须引用 `12 个月 3 次请求`、`+6 美元 BOM`、`改外壳/防水`、`手机可替代`、`路线聚焦训练/导航`；不能编造市场规模、渗透率、收入增量。
- `feasibility.technical` 应写“技术上可通过硬件改版实现”，不能误判为“技术不可行”；成本/依赖/风险要覆盖 BOM、结构/防水、认证、售后。
- `assumptions` 至少一条，以「假设：」开头，例如“假设：3 次请求不能代表整体用户需求”；`openQuestions` 至少包含重评触发条件（目标人群规模、愿付价格、与手机替代方案的关系），用于决定何时重评，不作为当前推进理由。
- `verdictReason` 应落在“价值/成本不匹配、需求频次低、与产品路线冲突”，不是“做不出来”。
- `investigationPrompt` 应以需求验证为主：目标用户访谈、同类替代、愿付价格、销量/成本假设；不能直接进入 PRD 功能设计。

**不得出现**

- 把“价值存疑”写成“技术不可行”；
- 用未提供的市场数据证明“有很大市场”；
- 因为只有 3 次请求就直接判 `advance`；
- 编造竞品销量、用户调研结果。

## 3. 目标环境执行注意

- 这四条只用于评估接口/面板验收；执行时用测试需求（或明确的测试标记），不写 Base，不触发 PM 通知。
- 评估结果按新表 `requirement_assessments` 落库；测试结束按测试数据规则清理评估行及其关联需求（如为验收新建）。
- 不得把样例文本当成真实用户需求导入生产池；A01–A04 全部为虚构。
