## 7. 已定的口径（Chief 2026-11-21 拍定）

1. 跨池 UUID **固定 404**，作为隔离验收第一条。
2. 编号 **跨池全局唯一、不回收**：本轮把 `MAX+1` 改为序列（迁移建 sequence、按现有最大值初始化、生成逻辑替换 + 并发用例）；两池共用全局编号。
3. 名单为空 **禁用同步**：数据源页禁止保存/启用并提示，接口侧不允许空名单启用。
4. **集团池不显示来源 Tab 和来源徽标**（只有一个来源）；产品池完全不变。
5. 集合接口（列表/计数/导出/批次）用**显式 `pool`**，缺省 `product`；**详情与写接口不传 `pool`**，一律从需求自身的 `source_config.pool` 推导。
6. **审计本期不做分池筛选**，同步记录页只按批次池筛选并注明限制。

待产品/后端补充的仍有两项：集团池 Base 表与通知收件人由谁配置；总览页是否显示集团池卡片（还是只从侧边菜单进入）。

## 9. 隔离边界说明（会写进最终验收结论）

- 本项目的「池隔离」是**数据作用域隔离**，不是**权限隔离**：同租户登录用户对两个池都有访问权，现有访问模型没有按池的角色矩阵。
- 因此 `GET /api/requirements/{UUID}` 不带 `pool` 时返回 200 + 只读 `pool` 字段，**是设计如此**；跨池阻断由前端按 `detail.pool` 守卫（页面显示 404 态）。
- 验收**不把**「无 `pool` 的 API 返回 200」列为越权漏洞。判 FAIL 的只有四类：
  1. 显式 `pool` 与归属不符仍返回数据/空 200；
  2. 列表/计数/导出/批次接口串池；
  3. 页面守卫失效，集团池路由展示了产品池数据（或反向）；
  4. 写操作能通过传 `pool` 改变归属。
- 若将来要真正的跨池鉴权，需要另行定义角色矩阵，超出本轮范围。
