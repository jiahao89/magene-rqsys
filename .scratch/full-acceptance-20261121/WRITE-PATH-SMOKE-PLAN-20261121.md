## 4. 步骤与判据

### S1 分配负责人（应用）

- 操作：详情页「分配 / 变更负责人」→ 选 §2 确定的账号 → 保存（等价 `PUT /owner`）
- 期望：`ownerState=manually_mapped`、`ownerName=<X>`；响应 200 且提示已排队推送
- 证据：截图 + 详情 JSON

### S2 Base 回写（应用 → Base）

- 期望（1 分钟内，必要时手动刷新）：
  - `负责人` = X（人员字段）
  - `系统通知事件ID` = `owner_changed:5f0c8561…:sv1:avN:…`（**必须以 owner_changed 开头且含需求 UUID**）
  - `系统通知类型` = 负责人变更
  - `系统通知收件人` = [X]
  - `最后推送时间` 更新
  - `推送状态` 仍为 已推送
- 判据 W2：以上 5 项全对

### S3 通知实收（IM）

- 期望：X 的飞书收到一条「需求通知」卡片，标题含需求标题、按钮「查看需求」可跳到应用详情
- 判据 W3：X 回复「收到」+ 卡片截图（这是 IM 投递的唯一硬证据）
- 注意：**只应收到 1 条**；若其他人也收到，立即记录并停止后续步骤

### S4 应用读回（Base → 应用）

- 操作：刷新详情，查看「处理与推送 / Base 记录」区块
- 期望：负责人显示 X、PM 快照与 Base 一致；无「推送失败」；无 `base_config_missing`
- 判据 W4：读回一致、无错误码

### S5 撤销（回滚 = 正常步骤）

- 操作：详情页「恢复默认负责人」（等价 `DELETE /owner`）
- 期望：`ownerState=pending_mapping`、`ownerName=null`；再排队一次推送
- Base：`负责人` 清空；`系统通知事件ID` 变为新的 owner_changed 记录（收件人为空）；`推送状态` 已推送
- 判据 W5：App 与 Base 都回到「无人」，**不再产生新通知**

### S6 收尾复核

- `source-counts` 产品 334 / 集团 191 不变；产品 Base 334 / 集团 Base 191 不变
- `batches?pool=product` 不新增批次（冒烟不触发同步）
- 审计新增：负责人变更 + 推送各 1 条（允许 2 条）
- 判据 W6：计数不变、无新批次、审计有记录

## 6. 回滚与失败处理

| 场景 | 处理 |
|---|---|
| S1 保存失败（400/409） | 不重试；记录错误码，检查 `ownerState` 是否允许手动负责人 |
| S2 Base 未更新（>5 分钟） | 看 `ops/jobs?pool=product` 是否新 failed；用详情「重试 Base 推送」一次；仍失败按缺陷记 |
| S3 通知错发他人 | 立即停止；截图留证；由 Chief 向对方说明；不继续 S4–S6 |
| 任一步骤卡住 | 直接执行 S5 撤销（DELETE），把状态回到无人；已写的事件ID 无法还原为旧值，属可接受副作用 |
| 冒烟结束后 | 无需删数据：需求本身保留，负责人为空即原状 |
