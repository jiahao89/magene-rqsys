## 1. 范围与判定

### 1.1 本轮要证明什么

1. 线上版本确实包含补丁（契约字段、UI 修复、错误码分层）——P0。
2. 方案 §4 的 5a 完成判据：**目标环境粘贴 5 段真实聊天 → 草稿字段可用 → 人工确认创建 → 走完 分析 → 推送**。
3. 负向边界在线上可解释：限流 429、未登录、空/超长输入、PII 不落库、枚举与词典外值被丢弃、幂等重提不重复建单。
4. 新增行为的线上表现：草稿不静默覆盖、编辑后撤销「AI 填充」标记、429/503 与 `Retry-After` 文案、`intakeOrigin`／`proposerName` 落库与展示。

### 1.2 不在 5a 范围（不要当缺陷记）

- 多维表格同步（5b）：收集表、Base 分页读、`base_form` 迁移、写回、运维可见。
- 5c：需求池来源筛选、四值来源徽标、指标按来源拆分、SOP 增补、Base「来源方式」字段。
- 语义相似需求（当前只做标题子串匹配）、相似需求跳转入口。
- 姓名进模型的 PRD 例外细则（由软件产品在 PRD-26 §5 补，不在本次功能验收）。
- 已知取舍：限流为进程内计数（多实例各自计数、重启归零）；日上限 100 不是跨实例硬限额。

### 1.3 判定等级

- **P0（阻断）**：版本不对、创建失败、分析→推送不通、PII 原文落库/入 Base、越权可调用、补丁声明的行为缺失。
- **P1（严重）**：错误码/文案不符、幂等失效、AI 标记不撤销、草稿覆盖、限流不生效、审计缺失。
- **P2（可记录后放行）**：相似需求未命中、延迟偏高、文案瑕疵、目标环境无法构造的边界。

每条用例记录：`PASS` / `FAIL` / `BLOCKED` / `OBS`（观察到但与预期不同的可接受现象，需注明理由）。

## 2. 数据影响与前置授权

### 2.1 会产生什么

- **5 条真实需求**（A 区 S1–S5 各一条）进入线上需求池，并推送到生产 Base「TB需求池」。**应用没有删除需求的接口**，创建后无法回滚；只能由 PM 用「重复处理 → 忽略」压制（记录保留，Base 行也不会自动删除）。
- 额外消耗：约 10–14 次 AI 抽取（含限流用例），5 次 AI 分析；均为现有额度，量级很小。
- 聊天原文**不落库**；但会先做 PII 掩码再发给模型（这是产品既定行为）。
- 首推静默（`first_push` 不写通知字段、不触发负责人通知）；验收期间**不要给这些需求分配负责人**，否则会通知到真人。

### 2.2 必须拿到的授权

- [ ] 用户/发布负责人同意在生产池创建 5 条验收需求。
- [ ] PM（Base 使用方）知情：标题统一加 `[验收] ` 前缀；验收结束由 PM 决定是否标记忽略。
- [ ] 确认执行窗口内没有其他人做 PRD-26 相关测试（限流按账号计数，会互相干扰）。
- [ ] 真实聊天原文如含客户真实手机号/邮箱/证件号，**粘贴前替换为同格式测试值**（如 `13812345678`、`test@example.com`、`110101199001011234`）；掩码是正则行为，测试值与真实值等价，且避免真实 PII 进入验收环境。

### 2.3 执行顺序（按此顺序可避免互相污染）

1. P0 执行前检查 → 2. A 抽取与创建（5 段，段间隔 ≥20s，避免撞 3/分）→ 3. B、C、D、G、H → 4. I 全链路轮询 → 5. F 幂等（用 A 中已创建的一条捕获请求重放）→ 6. E 限流（放最后，避免影响前面的抽取）→ 7. J 审计与日志复核。

## 4. A：5 段真实聊天抽取 + 确认创建（方案 §4 完成判据）

### 4.1 样本定义（真实聊天，粘贴前按 §2.2 处理 PII）

| 样本 | 聊天特征 | 重点验证 |
| --- | --- | --- |
| S1 | 明确的功能诉求，提到渠道（如「售后反馈」「终端用户」）和一个已发布模块名 | 标题/描述整理质量、渠道、模块 |
| S2 | 含手机号、邮箱、身份证号、`@某人`、24 位十六进制平台用户 ID | PII 掩码、枚举不猜、提出人 |
| S3 | 口语化、多轮寒暄、没有明确渠道和需求类型 | 渠道/类型留空不猜；无关信息不进描述 |
| S4 | 长文本（≥1,500 字），含多个诉求、数字、期限 | 20,000 字上限、约束说明、描述整理 |
| S5 | 明确写了提出人姓名 + 与需求无关的闲聊 | `proposer` 抽取、姓名只用于展示 |

### 4.2 每段抽取的记录表（S1–S5 各填一行）

| 项 | 预期 |
| --- | --- |
| 响应耗时 | 记录；超过 20s 或前端一直「整理中…」记 FAIL |
| `title` | ≤200 字、中文、无「张伟 2026-11-18 09:12」这类聊天头、不是整段原文 |
| `description` | 有整理结构（提出人/问题/诉求/目的任一合理分段），**不编造聊天里没有的事实** |
| `sourceChannel` | 聊天有明确渠道则为对应枚举；不明确必须为 `null`，不得猜 |
| `requirementType` | 有依据才填，否则 `null` |
| `productModel` / `constraintNotes` | 聊天提到才填；期限/兼容性进约束说明 |
| `intakeModule` | 必须是已发布词典里的名称，否则 `null` |
| `proposer` | 聊天明确提到才填；口语化的「客户」不算人名 |
| `aiFilled` / `aiFilledCount` | 二者数量一致；只包含 AI 填了非空的字段；标题/描述来自兜底时不得计入 |
| `fallback` | 正常应为 `false`（`true` 见 K-1） |
| `similar` | ≤5 条；有命中时 id/RQ 号可见；无命中为空数组 |
| 草稿是否入库 | 未点提交前，需求总数、审计 `intake.created` 均不增加 |

| ID | 步骤 | 预期 | 实际 | 结论 |

| K-1 | `fallback=true` 与「未经 AI 整理」提示 | 真实模型不会稳定返回不可用输出 | `chat-extract` 单测 + Web 组件测试 | 线上偶发兜底时提示是否可读，只能靠代码审阅 |
| K-2 | 供应商 429 → API 429 + `Retry-After` | 无法让上游限流 | `chat-extract`／`app.test` 单测 | 上游 429 与本地 429 文案需区分 |
| K-3 | `auth_error`／`request_error` → 500 + 服务端日志 | 不能改生产密钥 | 单测 + 本地 dev 日志 | 500 是否告警取决于日志接入 |
| K-4 | `timeout`／`network_error`／`analysis_failure` → 503 | 不能制造供应商故障 | 单测（含 Abort 超时） | 客户端 503 文案是否可重试 |
| K-5 | 409 的 UI 出口「换新键重提」 | 需要「已提交成功但响应丢失」的故障注入 | Web 组件测试 | 真实网络抖动时是否可自愈 |
| K-6 | 日上限 100/天 | 打满会烧额度且污染当天配额 | 单测（日窗口边界） | 多实例/重启后日限是近似值 |
| K-7 | 提交失败后复用同键重试 | 需拦截响应 | Web 组件测试（已有一条 503 重试用例，需扩展到新键轮换逻辑） | 网关 502 后误换键 |
| K-8 | AI 额度暂停 → 503 | 暂停开关没有对外入口 | 单测 | 真实暂停时用户是否理解 |
| K-9 | 多实例/重启后的限流 | 客户端无法分辨实例 | 无（已知取舍，文档声明） | 成本刹车失效风险 |
| K-10 | 超过 20,000 字的请求体不被提前缓冲 | 平台 body-parser 在前 | 无（P2，不在本次范围） | 内存放大 |
| K-11 | 抽取后、提交前词典变更导致模块失效 | 不能在生产改词典 | 单测（提交时词典校验） | 用户收到 400 的文案 |
