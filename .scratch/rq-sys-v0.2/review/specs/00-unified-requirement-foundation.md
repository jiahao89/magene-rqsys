# V02-S00 — 统一需求身份、来源与模块职责

> 状态：draft — 待确认测试接缝与任务拆分，尚未发布到正式任务目录。
> 基线：V0.2 本地 PRD（2026-10-22）；继承 MVP 不冲突的契约及 D-12 最新通知规则。
> 本文是增量约束，不表示相关功能已实现或已通过目标环境验收。

## Problem Statement

当前需求事实、后台作业和 Base 查询都隐含“每条需求必有 TB 来源”。销售、售后或产品内部的手工需求无法直接进入同一工作台；若使用假 TB ID 或按标题合并，会丢失来源、形成重复推送或覆盖另一条需求。

## Solution

在现有模块化单体内增加来源无关的需求记录和收录接口，保留 TB 原始身份，统一由稳定平台 ID 关联需求详情与 Base；继续使用已有队列、版本、审计和平台适配。

## User Stories

1. 作为录入人，我希望手动需求不需要 TB ID 或同步配置，以便及时记录其他渠道反馈。
2. 作为 PM，我希望 TB 和手工需求出现在同一需求池，以便按同一流程处理。
3. 作为 PM，我希望来源类型与业务来源渠道分开展示，以便区分接入方式和反馈来源。
4. 作为录入人，我希望重复提交返回同一个需求，以便网络重试不会多建记录。
5. 作为 PM，我希望平台需求 ID 一经生成就不变，以便跨版本和跨系统追溯。
6. 作为 PM，我希望不同来源、不同源 ID 的同标题需求独立保留，以便相似描述不掩盖不同诉求。
7. 作为维护者，我希望已有 TB 记录、来源版本和 Base 关联继续有效，以便升级不丢历史。
8. 作为录入人，我希望手动收录显示“已收录”，以便不会误认为需求已同步自 TB。
9. 作为 PM，我希望 AI、负责人和推送进度各自显示，以便准确理解部分成功。
10. 作为维护者，我希望任务重启后能恢复，以便建单成功后不会永久漏分析或漏推送。
11. 作为维护者，我希望根仓与妙搭仓遵循相同业务契约，以便本地正确的功能在目标环境也一致。
12. 作为成员，我希望沿用飞书登录即可使用的访问规则，以便无需新增角色审批。
13. 作为维护者，我希望数据库升级保留旧记录和旧读取能力，以便可以安全分批发布。
14. 作为 PM，我希望来源事实、AI 建议和人工处理值有清晰归属，以便更新不会覆盖人工判断。

## Implementation Decisions

- 需求身份分三层：内部 UUID 用于关联；不可变 RQ-编号用于展示及 Base 跨来源定位；TB 项目和 TB 需求 ID 只用于 TB 来源去重与追溯。不同源 ID 或不同来源不按标题自动合并。
- 来源类型首期仅 teambition、web_manual。来源渠道是独立业务属性，采用 PRD 已列渠道类别；本期无外部连接器框架。现有来源配置仍只配置 TB 项目和周计划，不为手工需求伪造同步来源。
- 增量扩展现有需求表：来源类型有默认 TB 值；TB 来源继续要求有效来源配置与 TB ID，手工来源允许这些列为空。保留 TB 身份唯一约束，并加来源分支一致性约束、平台编号唯一约束及必要查询索引。
- 平台编号复用现有事务锁和分配能力；TB 导入与手工创建使用同一分配器。保留旧号，只回填缺失号；请求重放不分配新号，回滚不得留下半条需求。至少六位，超过六位时不得截断。
- 建立收录与需求命令模块，封装校验后的创建/更新、幂等、版本、审计与持久任务调度。HTTP 只负责可信身份、契约和响应；TB 适配仍只负责拉取/规范化；运行时负责注入已有仓储与外部适配器。避免另造一套完整工作流。
- 只抽取本次变更涉及的需求功能模块；不整体迁移框架、不统一两个平台数据库驱动，不以新增转发层作为结构优化。新增共用业务模块须纳入双仓对齐约束；平台差异通过同一行为用例验证。
- 跨来源列表的负责人、来源筛选和统计须按每条记录的来源解释，不能以第一页首条记录的TB配置决定整页映射；手工空TB ID不得被SQL过滤条件误当作夹具或漏出统计。主读取接口增加来源类型和来源收录状态；TB 现有 pull 字段语义保留。手工记录使用 collected 语义，TB 拉取状态为空或明确不适用；后台就绪判断基于来源快照已持久化，不能要求所有来源 pull=synced。
- 手工创建在同一数据库事务中保存需求、首个来源快照、可信 actor 审计、幂等回执和可恢复分析作业。失败时整体回滚；作业消费在事务提交后进行，复用现有租约、去重和恢复机制。
- 业务 API 仍只有一个 OpenAPI 契约来源。后续实施先以加法更新契约，再同步请求校验、DTO、前端客户端和妙搭路由；不另设互相冲突的 V0.2 契约副本。
- Base 仍持有 PM 状态、PM 确认模块/优先级等协作值；Web 拥有手工需求事实、录入模块及人群标签。Web 的“录入模块”不冒充 Base 的“PM确认模块”，这是本草案建议的最小数据归属方案，待一并确认。
- 所有已登录租户成员可使用新增接口，actor 只来自可信登录上下文。“负责人填写 RICE”是业务责任，不自动引入角色权限矩阵。
- 迁移采用扩展—兼容读取/写入—核对回填—切换—收缩顺序。手工写入开启前，两仓运行时及 worker 必须理解新来源；已存在手工数据时不得回退至 TB-only 旧二进制。

## Testing Decisions

- 主接缝为受保护的现有应用 HTTP 入口：通过创建/读取/更新需求与正常 worker 消费观察行为；不新增只供测试使用的业务接口。
- 数据库约束、幂等并发和事务失败使用真实本地 PostgreSQL 的独立临时 schema 验证，沿用现有仓储集成测试做法；内存假库不能证明唯一约束或锁行为。
- 真实仓储与生产 worker 编排配合受控 AI/Base 适配器，断言最终记录、版本、状态和外部有效载荷，不断言内部函数调用顺序。
- UI 沿用现有需求池及面板测试，覆盖来源标签、空态、重试与错误恢复。妙搭沿用真实控制器/路由测试入口，不以根仓通过替代目标平台验证。
- 目标环境需核对旧 TB 数据和新手工记录的身份/版本/Base 关联；观察完成前只能记为本地已实现。

## Out of Scope

- 本期接入售后、电商、社媒等更多外部 API；完整 28 字段和全生命周期管理。
- 自动跨来源合并、按标题删除或隐藏需求、TB 回写、替换框架或拆微服务。
- 新 RBAC、Base PM 状态或通知送达结果回写 Web。

## Further Notes

- 当前代码有同标题过滤行为，与 AGENTS 的源 ID 不变量冲突；必须作为独立决策/修正任务核对，不能在通用来源模块中默认继承。
- 本草案的结构调整是增量方案；正式批准后再记录为 V0.2 ADR，并同步 V0.2 适用的领域词汇和 Agent 指引。
