# V02-S01 — Web 新建、编辑与需求级负责人

> 状态：draft — 待确认测试接缝与任务拆分，尚未发布到正式任务目录。
> 基线：V0.2 本地 PRD（2026-10-22）；继承 MVP 不冲突的契约及 D-12 最新通知规则。
> 本文是增量约束，不表示相关功能已实现或已通过目标环境验收。

## Problem Statement

当前只有 TB 同步入口和 TB 人员映射，无法直接创建来自其他渠道的需求，也无法在不影响其他需求的前提下为手工需求保存负责人。

## Solution

增加精简新建表单和手工需求编辑，直接选择需求级负责人；提交后自动进入已有主分析和 Base 推送，缺少负责人或 AI 证据不阻断收录。

## User Stories

1. 作为录入人，我希望从需求池新建需求，以便录入没有进入 TB 的反馈。
2. 作为录入人，我希望只必须填写标题、描述和渠道，以便降低录入负担。
3. 作为录入人，我希望看到用户、场景、问题和期望的提示，以便补全需求而不被长表单阻塞。
4. 作为录入人，我希望按需填写产品、需求类型、限制和补充链接，以便保留明确上下文。
5. 作为录入人，我希望创建后立即得到平台编号和详情入口，以便确认提交结果。
6. 作为录入人，我希望网络失败后重试不会再建一条需求，以便放心恢复操作。
7. 作为 PM，我希望创建时可以选择字典模块，以便给分析和分流提供上下文。
8. 作为 PM，我希望模块责任人只作为候选提示，以便由人确认真实分配。
9. 作为 PM，我希望同一个人可以负责多条手工需求，以便不会触发 TB 映射唯一性冲突。
10. 作为 PM，我希望改派一条需求不会修改别人的需求，以便分配行为保持局部。
11. 作为录入人，我希望无负责人也能提交和推送，以便后续再分配。
12. 作为 PM，我希望能修改手工需求定义并保留历史，以便反馈逐步澄清。
13. 作为 PM，我希望 TB 事实仍由 TB 更新，以便不会在两个入口互相覆盖。
14. 作为 PM，我希望并发编辑时明确提示版本冲突，以便不覆盖他人的修改。
15. 作为 PM，我希望编辑后旧 AI 结果不冒充新版本结论，以便正确理解分析依据。
16. 作为 PM，我希望实质变更在 Base 更新前保护已有 PM 值，以便不丢协作记录。
17. 作为负责人，我希望人工分配及改派成功推送后收到通知，以便及时处理。
18. 作为维护者，我希望重启、重复提交和旧任务迟到都可恢复，以便流程不会停在中间。

## Implementation Decisions

- 必填标题、描述、渠道；其余字段按 PRD 可空。描述是一个文本字段，四段提示不转成四个强制字段。只做必要长度/类型、枚举和来源链接格式校验，不增加人为业务门槛。
- 创建接口采用 POST 需求集合；详情和列表复用现有查询。手工编辑使用 PATCH 需求资源及期望版本；创建/编辑均要求请求幂等键。相同 actor/操作/键和相同请求返回原结果，同键不同内容返回冲突。actor 与创建时间不得由客户端指定。
- Web 表单在同一次提交重试时保留幂等键；成功后清除。提交状态必须区分“已保存、处理中”与“Base已推送”，不得假成功。
- 需求级分配保存飞书 ID、显式 ID 类型、分配来源、递增分配版本、操作者和历史。不得把手工需求写入 TB 人员映射，也不能把需求级分配变成对所有同名 TB 人的全局改派。
- 复用现有人员目录/飞书用户选择与服务端身份解析；一个人可负责任意多条需求。模块关联人员只是候选，用户明确确认后生成分配命令；AI 不直接分配。
- Web 录入模块与 AI 模块建议独立存储；Base PM确认模块继续由 Base 持有。修改录入模块不覆盖 AI 历史或 Base PM确认模块。
- 手工内容更新按预期版本比较、持久化新快照、审计和任务。规范化后无变化不新建来源版本、不新建分析、不重复推送。对产品/型号、问题描述、约束等影响含义的更改重跑主分析；渠道或追溯链接等元数据更改不自动重跑。
- 负责人和人群修改采用独立版本/历史，不强迫伪造 TB 源版本变化。并发内容编辑不得丢失独立负责人、人群修改。
- 旧分析/旧推送作业只能结算其对应来源/实质版本；源内容已更新时，旧结果不得成为当前结果、覆盖新状态或把旧内容写回 Base。复用既有 worker fencing，再补齐版本检查。
- 主流程在首次分析成功、失败或超时终态后推进。未分配负责人允许空负责人推送；未映射 TB 负责人继续沿用现有待匹配规则，不在本期无声更改该规则。
- 手工事实可编辑，TB 事实只读；人群及通用人工分配按各自规则处理。显式撤销已分配负责人并清空 Base 负责人不纳入本期，避免与保护 Base 人工分配的规则冲突。
- 前端仅按需求功能抽出表单、详情编辑和 Beta 挂载位，继续使用当前 UI 规范与路由，不将新功能继续堆进跨业务的全局面板。

## Testing Decisions

- 通过已登录应用 API 创建/读取/修改需求并消费正常后台队列，检查相同需求 ID、来源快照、审计及 Base 最终行；不单测表单实现细节。
- 覆盖并发相同请求、同键不同内容、保存中断、入队失败回滚、并发编辑冲突、无变化编辑、旧分析迟到、worker 重启恢复。
- 复用现有负责人/推送路由测试与需求详情刷新测试；增加同一负责人对应多条手工需求且改派互不影响的行为用例。
- UI 验证键盘可操作、失效模块/人员提示、必填错误、未提交内容保留及成功跳转。
- 目标环境以安全手工需求验证已收录→分析终态→POC Base；通知只允许指定测试账号，正式流转须另行发布确认。

## Out of Scope

- TB 原始事实在线编辑/回写、跨来源合并、附件上传、草稿箱、复杂审批与业务状态回写。
- 负责人自动指派、为新功能增加角色权限、清空 Base 中已有人工负责人。
