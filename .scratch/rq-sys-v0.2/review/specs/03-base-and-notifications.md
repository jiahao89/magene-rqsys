# V02-S03 — 跨来源 Base 投影、迁移与通知

> 状态：draft — 待确认测试接缝与任务拆分，尚未发布到正式任务目录。
> 基线：V0.2 本地 PRD（2026-10-22）；继承 MVP 不冲突的契约及 D-12 最新通知规则。
> 本文是增量约束，不表示相关功能已实现或已通过目标环境验收。

## Problem Statement

Base 当前按 TB ID 查找；手工需求没有该 ID。直接切换或重复重试可能创建第二行，人工分配与 Base 中的负责人也可能被旧映射覆盖。

## Solution

将稳定平台编号作为跨来源 Base 键，兼容已有 TB 行并保护 PM 字段；需求级分配与内容/分析事件沿用单收件人通知策略。

## User Stories

1. 作为 PM，我希望两种来源在 Base 各有一条稳定记录，以便集中协作。
2. 作为维护者，我希望已有 TB 行被复用，以便升级不产生第二份历史。
3. 作为 PM，我希望手工需求的 TB 专属字段为空，以便不会看到假 TB ID 或假链接。
4. 作为 PM，我希望来源字段和人工字段可区分，以便清楚谁负责修改。
5. 作为 PM，我希望重试和写入超时不会重复建行，以便可安全恢复。
6. 作为 PM，我希望实质内容变化前保存当前处理值，以便可以追溯原判断。
7. 作为 PM，我希望只改元数据不重置业务状态，以便不被重复要求受理。
8. 作为 PM，我希望空/未解析来源负责人不擦除 Base 人工负责人，以便分配可持续。
9. 作为负责人，我希望被人工分配的首次推送就通知我，以便知道自己有任务。
10. 作为负责人，我希望改派只通知新负责人，以便减少干扰。
11. 作为负责人，我希望内容变更或 AI 重试成功通知当前负责人，以便收到相关更新。
12. 作为 PM Leader，我希望无负责人时承接内容/分析变更消息，以便没有遗漏。
13. 作为 PM Leader，我希望自动匹配的批量首次推送保持静默，以便避免消息洪水。
14. 作为成员，我希望重复同步不重复通知，以便关注真正变化。
15. 作为维护者，我希望不同飞书 ID 类型被正确处理，以便避免人员字段转换失败。
16. 作为维护者，我希望查到键冲突时停止该条而不是错误合并，以便保护业务数据。
17. 作为 PM，我希望 Web 显示推送成功而不虚称消息已送达，以便理解证据范围。

## Implementation Decisions

- Base 跨来源首选键为需求平台ID。先查平台键；TB 行迁移期间仅在已配置项目内允许按旧 TB ID 查到唯一旧行并补平台键。匹配多行、平台键不一致或旧关联冲突时停该条并审计，不自动合并或另建。
- 旧代码和 worker 停止写入后才能开启手工来源与平台键模式；先核对平台编号回填、Base记录关联和兼容运行时，再切换。已经回填的编号不重新分配。
- Base 查找与创建受现有需求级分布式串行保护；外部创建结果不确定时，重试必须先对账平台键与已保存 recordId。缺少 Base 原生唯一约束不能被宣称为无条件 exactly-once；查找不确定/冲突时停止创建。
- TB ID/地址是仅 TB 适用的投影，手工来源不构造伪值；TB项目ID不增加回正式表。旧 TB 列的删除只在无旧读写依赖并有目标回读证据后执行。
- 投影只包括需求定义、来源追溯、批准 AI 主结果、负责人和现有协作字段；新增列先验证目标类型，再写入。来源类型、渠道、产品及时间使用通用命名，TB专属字段明确TB来源。
- PM状态、PM确认模块/优先级、处理人/时间和结构化备注继续属于 Base。Web录入模块不覆盖PM确认模块；人工人群值不伪装成AI建议。未知模块/超单选项上限沿用有记录的省略策略，不因扩展来源伪造有效值。
- 实质变化先读Base并持久化PM快照，再写同一行、置待处理。快照失败时不得修改该行；无变化或仅元数据/人群修改不触发重置。
- 人工分配作为有版本的明确命令写Base；后续没有新分配命令的内容/AI更新不得反复用旧本地分配覆盖Base中的人工改派。TB新负责人可匹配时沿用已确认的变更规则；空或未解析TB负责人保持Base人工值。
- 当前收件人取本次有效分配或目标Base当前负责人；推送过程读取Base负责人仅服务字段保护/事件选人，不新增Web业务状态回读。无法读取不等于“没有负责人”，不能因此误发PM Leader。
- D-12通知表：自动匹配批量首推静默；人工分配首推通知被分配人；分配/改派通知新负责人；内容变更和AI重试成功通知当前负责人，无负责人时通知PM Leader王赵云；提出人不通知。
- 内容通知按实质来源版本去重；分配通知按分配版本及新旧身份去重；AI重试成功通知包含分析版本，不能只按源版本折叠所有后续成功事件。一次有效事件只有一个收件人。
- Base upsert失败不写成功通知事件；重放同事件不再次发消息。业务行与通知系统字段分段写入中断时可用同事件身份恢复，不能重新生成另一个事件。送达重试与记录仍由Base自动化承担，本期不引入Web送达看板或自建消息服务。
- 人员身份始终保留ID类型。需要分别写负责人和不同ID类型收件人时，沿用当前分段写入并验证失败恢复，禁止给ID错误标记类型。

## Testing Decisions

- 通过需求API和正常worker驱动真实push模块，已有BaseClient/transport作为外部接缝。验证最终字段、相同recordId、快照历史和事件身份，避免mock每个内部步骤。
- 覆盖平台键命中、旧TB唯一命中、冲突多行、创建超时但已落行、重复作业、混合来源同标题、缺少TB字段。
- 覆盖快照失败不写、实质更新置待处理、元数据不重置、Base已有手工负责人不被旧本地映射擦除。
- 通知表逐项覆盖，包括同一源版本多次不同AI成功结果、A→B→A、不同ID类型分段写入和通知字段失败补偿。
- 目标POC独立回读Base记录和本人收件，记录脱敏的需求/版本/事件/记录ID与时间；未观察到收件不能以字段已写代替送达通过。

## Out of Scope

- 多收件人、Web消息送达状态、通知权限管理、自建消息分发、全28字段、Base业务处理状态同步。
- 本轮执行正式表变更、发布或给干系人发消息；本轮仅拆Spec/Tickets。

## Further Notes

- 现有Base负责人变化自动化必须与应用通知系统事件共同抽检，避免人工分配同时触发两条消息；不能只验证某一个入口。
- 兼容切换与正式通知启用是目标环境门槛，需沿用项目现有写入授权流程。
