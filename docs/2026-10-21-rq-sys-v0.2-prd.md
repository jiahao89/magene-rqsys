## 1. 背景与目标

现有 MVP 以单一 Teambition 项目为入口，需求事实结构和推送键也围绕 TB 字段设计。实际需求还会来自售后、销售、运营、用户反馈及产品内部等多个渠道。V0.2 首先增加 Web 手动新建需求，让这些尚未进入 TB 的需求也能进入同一需求池，并复用已有的 AI 分析、负责人分配、Base 推送与飞书通知。

V0.2 目标：

1. 支持记录 TB 同步及 Web 手动新建两种来源；来源渠道作为业务属性记录，后续外部系统接入按独立连接器迭代，不要求本期接入所有渠道。
2. 新建需求只收集定义和流转所需的精简字段，使用系统生成的 RQ-Sys 需求平台 ID，并进入现有 AI→负责人→Base→通知链路。
3. 默认分析仍以 U/M/S/C 为主，并通过经校准、版本化的规则生成 P0–P3；RICE 和 Kano 不参与默认优先级。
4. RICE 与 Kano 放在需求详情的次级 Beta 入口中，由用户按需触发。Beta 结果不阻断创建、分析或推送，也不覆盖 U/M/S/C 与 PM 确认值。

## 2. 目标用户与对象

### 2.1 使用角色

- **需求提出人 / 录入人**：在 Web 新建需求；默认由当前登录账号记录为录入人，可提供来源渠道和必要上下文。
- **PM / 产品组成员**：查看 U/M/S/C 与模块建议，确认或修改适用人群、模块和负责人；需要时打开 Beta 工具。
- **需求负责人**：在 Beta 中手动填写并确认 RICE 输入；不填写也不影响主流程。
- **系统**：保存来源、需求版本、AI 分析、负责人和推送记录；跨来源使用同一需求详情和后续流转能力。

### 2.2 用户人群字典

需求可关联一个或多个六层人群标签：

| 层级 | 名称 | 英文名 | 使用说明 |
|---|---|---|---|
| L1 | 职业级 | Pro | 职业车手及以骑行为职业的人群 |
| L2 | 竞技级 | Racing | 参加竞技、追求成绩和训练表现的人群 |
| L3 | 爱好者 / 专业入门 | Enthusiast | 有规律骑行并向系统训练或竞技进阶的人群 |
| L4 | 健身锻炼 | Fitness | 以健身、运动和健康管理为主要目的的人群 |
| L5 | 休闲娱乐 | Recreation | 以骑游、亲子、旅行和休闲体验为主要目的的人群 |
| L6 | 通勤代步 | Commuter | 以日常通勤或代步为主要目的的人群 |

人群标签描述需求适用的目标人群，不作为用户个人档案或用户身份识别。地区、国家和产品线等维度可作为独立上下文，不并入六层标签。

## 3. 用户流程

### 3.1 默认需求处理主流程

```mermaid
flowchart LR
    A[TB 定时/手动同步] --> C[统一需求池]
    B[Web 新建需求] --> C
    C --> D[保存来源事实与版本]
    D --> E[AI 分析：模块、人群、置信度、U/M/S/C]
    E --> F{优先级规则已发布?}
    F -- 是 --> G[按规则确定 P0-P3]
    F -- 否 --> H[优先级留空并显示待校准]
    G --> I[负责人确认/分配]
    H --> I
    I --> J[幂等推送飞书 Base]
    J --> K[按已确认通知规则通知负责人]
```

1. TB 需求继续按 MVP 流程同步；Web 新建需求由录入人提交。两种来源使用同一需求详情和后续 AI、负责人、Base 推送流程。
2. AI 对来源文本给出受控功能模块、整体置信度、适用人群建议和 U/M/S/C 维度建议；理由、证据和缺失信息分开展示。
3. P0–P3 只从已发布的 U/M/S/C 规则确定性计算。规则未发布时保持空值，Beta RICE/Kano 不代替、不补算优先级。
4. 负责人可由模块责任人作为候选建议，最终由录入人/PM 确认或在详情中人工选择；未分配负责人仍允许推送。
5. Base 按需求平台 ID 更新同一条记录；负责人通知沿用当前已确认的 MVP 通知策略。新建需求人工指定负责人后首次推送，应通知该负责人；未分配负责人仍可推送且不向虚构收件人发消息。

### 3.2 新建需求流程

1. 用户在需求池点击“新建需求”，填写标题、需求描述、来源渠道；产品/型号、需求类型、边界限制和补充说明按实际情况填写。
2. 需求描述提供“用户/场景—现状问题—期望结果”的填写提示。标题和描述是提交必填项；四段内容不完整时可以保存并继续流转，由 AI 标出缺失项，不因信息不完整阻断推送。
3. 系统记录当前登录人为录入人，生成连续且不可变的 RQ-Sys 需求平台 ID，保存第一个来源快照并排入主 AI 分析。
4. 用户可以在创建时选择功能模块和负责人；若模块已绑定负责人，可预填为候选，但不静默替用户作出分配。负责人字段可以留空。
5. AI 首次尝试结束后，按现有规则进入负责人匹配与 Base 推送；低置信度、缺失维度、AI 失败均不阻断可推送需求。
6. 后续编辑需求定义字段时，保存新版本、重跑主 AI 分析，并更新同一条 Base 记录；在更新前先按现有规则快照 PM 字段，更新后将 PM 状态置为“待处理”。

### 3.3 可选 Beta 流程

Beta 不参与定时分析或同步后的自动分析。用户在需求详情的“更多 / Beta 分析”入口手动启动 RICE 或 Kano；每次结果独立保存、可追溯，关闭 Beta 面板不影响主需求流转。

姓名、手机号、邮箱和用户 ID 不作为模型输入。录入人身份由系统审计记录，不把登录身份直接拼进 AI 提示词。

#### 统一来源与数据归属

- V0.2 本期新增的非 TB 入口仅为 `web_manual`。渠道字段可描述需求来自售后、销售等场景，但不表示已连接这些外部系统或自动采集数据。
- Teambition 来源事实仍由 TB 持有；Web 手动创建的需求事实由 RQ-Sys 数据库持有。飞书 Base 是统一 PM 协作和通知投影，不反向成为两类需求的原始来源。
- RQ-Sys 数据库 ID / 需求平台 ID 是统一记录身份；TB 需求 ID、项目 ID 和 TB 地址作为 TB 来源专属的可空字段保留。Base 按需求平台 ID 幂等创建/更新，TB ID 仅用于来源追溯，不能要求手工需求提供 TB ID。
- Web 新建与编辑必须使用请求幂等键、审计记录和追加式来源版本。重复提交不应产生第二个需求平台 ID 或第二条 Base 记录。
- Base 字段只投影需求定义、来源追溯、AI 主流程结果、负责人和 PM 协作字段。不得把完整 28 字段一次性复制到 Base。

#### 主流程状态

| 场景 | 来源状态展示 | 后续状态 |
|---|---|---|
| TB 导入 | 已同步 / 同步失败 | AI 分析、负责人、Base 推送分别展示 |
| Web 新建 | 已收录 / 创建失败 | AI 分析、负责人、Base 推送分别展示 |

### 4.2 U/M/S/C 主评分与优先级

> 实现级契约、API、数据模型与票拆分见 [V02-S06](../specs/rq-sys-v0.2/06-ai-scoring-and-priority.md)；本节的公式、阈值和 α 口径是产品决策。

#### 4.2.1 目标与原则

- U/M/S/C 是默认、唯一影响主流程 P0–P3 的价值评估框架。
- **AI 直接评分**：AI 对九个评分输入项分别给出 1–5 或 1–3 的分数，并给出 α、依据、假设标记和说明；不再只给“高/中/低”。
- **服务端确定性计算**：正式综合分和 P0–P3 由服务端按已发布的评分 v2 规则计算，不采用模型自报的最终优先级。AI 可以在说明中给出试算综合分，但落库和展示以服务端结果为准。
- **人工可修订**：PM 可修改任一单项分数和 α，服务端立即按同一公式重算；不提供直接修改最终 P 或公式/阈值的入口。
- 评分明细、AI 建议、人工当前值和历史分别保存；人工修改不自动触发 Base 推送或通知。
- Kano 不在本期评分公式内；没有合格样本时保持“未评”，不伪造比例或样本量。RICE 仍是独立 Beta，不参与 U/M/S/C 或 P0–P3。

#### 4.2.2 评分输入

| 维度 | 输入项 | 取值范围 | 含义 |
|---|---|---|---|
| U 用户价值 | `pain` 痛点强度 | 1–5 | 1 几乎无感；3 明显不便；4 阻碍目标；5 涉及安全/不可逆后果 |
| U 用户价值 | `frequency` 发生频次 | 1–5 | 1 极少；3 每月；5 几乎每次骑行/每天 |
| M 市场价值 | `sellingPoint` 卖点强度 | 1–3 | 1 无对外卖点；2 可作对比支撑；3 核心差异化卖点 |
| M 市场价值 | `competitor` 竞品差异 | 1–3 | 1 未核实/无差异；2 与竞品持平；3 明显领先 |
| S 战略价值 | `roadmap` Roadmap 匹配 | 1–3 | 1 未规划/无证据；2 已列入候选或中期；3 当前版本/战略重点 |
| S 战略价值 | `dependency` 战略依赖/杠杆 | 1–3 | 1 独立单点；2 依赖现有平台但可复用；3 关键战略能力或跨产品协同 |
| C 成本 | `workload` 工作量 | 1–5 | 1 很小；5 很大 |
| C 成本 | `technicalRisk` 技术风险 | 1–5 | 1 很低；5 很高 |
| C 成本 | `resource` 资源占用 | 1–5 | 1 很低；5 很高 |
| α 修正系数 | `alpha` | 0.5–2.0，步长 0.1 | 证据强度/安全修正；默认见 4.2.3 |

所有输入项均为整数（α 为一位小数）。缺证据不是空值：AI 必须给出点估计，并标记 `assumption=true`、写明假设依据；置信度不足不得伪造成原文事实。

#### 4.2.3 计算规则

```text
U = pain × frequency                 （1–25）
M = sellingPoint × competitor        （1–9）
S = roadmap × dependency             （1–9）
C = MAX(workload, technicalRisk, resource)   （1–5）
U_adj = U × α
综合分 = round2( U_adj × (1 + 0.6 × M + 0.4 × S) ÷ C )
```

α 默认值：

| 场景 | 默认 α | 说明 |
|---|---:|---|
| 单条反馈/单渠道/无交叉证据 | 0.8 | 防止单点反馈被当作总体结论 |
| 多渠道或多条独立反馈 | 1.0 | 仍需在依据中说明来源数量与渠道 |
| 已确认涉及安全/不可逆后果 | 1.5 | 同时设置安全复核标记；不自动改 P，必须人工复核 |

PM 可在 0.5–2.0 范围内修改 α，并填写理由。α 不是“拍脑袋加分项”，修改必须记录在版本历史中。

P0–P3 阈值（本期唯一口径，不再使用其他阈值表）：

| 综合分 | 优先级 |
|---:|---|
| ≥ 45 | P0 |
| 25–44.99 | P1 |
| 10–24.99 | P2 |
| < 10 | P3 |

计算示例（历史试评，用于校准和回归）：

| 需求 | U（痛点×频次，α） | M | S | C | 综合分 | P |
|---|---|---|---|---:|---:|---:|---|
| 车灯模式选择 | 3×4，α=0.8 | 1 | 1 | 3 | 6.40 | P3 |
| Di2 换挡警示 | 4×4，α=0.8 | 1 | 1 | 3 | 8.53 | P3 |
| Di2（确认涉安全） | 4×4，α=1.5 | 1 | 1 | 3 | 16.00 | P2，转安全复核 |
| C706×GX 适配 | 4×5，α=0.8 | 4 | 1 | 4 | 15.20 | P2 |
| 媒体控制 | 4×4，α=0.8 | 4 | 1 | 4 | 12.16 | P2 |
| 传感器重命名 | 3×2，α=0.8 | 1 | 1 | 3 | 3.20 | P3 |

边界规则：C 最小值 1，因此不会除零；输入越界、非整数、非有限数或规则不完整时，不生成正式分和 P，保留上一次有效评分并提示修正。综合分按四舍五入保留两位小数；阈值按四舍五入后的分数判断。

#### 4.2.4 AI 直接评分与依据

AI 分析结果新增评分对象，必须同时包含：

- 九个输入项的整数分数、α 和每个输入项的依据；
- 每项依据：引用的原文证据，或 `assumption=true` 加明确的估算假设；
- 一段总体评分说明，解释为什么这些分数和 α 合理；
- 风险/安全标记及依据（若有）；
- 评分置信度（高/中/低）和理由。

硬性约束：

- 评分依据只能引用本次分析输入中的原文片段；不得编造竞品、Roadmap、研发工作量或用户频次事实。
- 没有证据时允许点估计，但必须标记假设；假设不得写成“已验证事实”。
- 输入越界、缺少依据/假设说明、证据不在原文中、α 不在范围内，均拒绝整条评分输出并进入可重试失败；不生成伪精确分。
- 模型不能直接写最终 P0–P3；服务端按公式计算。模型自报的优先级字段被忽略/拒绝。
- AI 评分失败不阻断需求创建、同步、负责人或 Base 推送；详情显示“评分待重试”，PM 可手动补齐。

#### 4.2.5 PM 修改单项评分和 α

详情页提供评分编辑：

1. PM 可修改任一输入项分数和 α；不能修改公式、阈值或综合分/P 本身。保存时服务端重算综合分与 P。
2. 每次保存必须填写修改理由；记录操作者、时间、修改前后值、版本号、评分置信度和 AI 原始建议。
3. 保存使用版本号做乐观并发控制；版本冲突返回 409，并在界面提示刷新后重试。
4. AI 评分与人工当前值分开保存。人工值不会被下一次 AI 重跑静默覆盖；详情同时展示“AI 建议”和“当前评分”。
5. 用户可选择“采用 AI 建议”：以 AI 最新建议的九项输入和 α 生成一个确认版本，记录操作者/理由；之后 PM 仍可继续修改。
6. 人工修改评分不自动重推 Base、不重置 PM 状态、不发通知、不启动 Kano/RICE。
7. 允许任何已登录的租户用户修改（V0.2 不引入 RBAC 角色矩阵）；所有操作以服务端可信身份记审计。

#### 4.2.6 评分版本与 AI 重跑

- 评分版本状态：`ai_suggested`（AI 新建议）、`current`（当前生效）、`confirmed`（人工确认）、`superseded`（历史）。同一需求只有一个当前生效版本。
- 分析或需求编辑触发 AI 重跑时，新建 AI 建议版本：
  - 当前没有有效评分：AI 建议自动成为当前；
  - 当前已有 AI/人工确认评分：不覆盖当前，详情展示新建议并提供“采用 AI 建议”；
  - 人工修改过的评分始终保留为当前，直到用户明确采用新 AI 建议或再次保存。
- 每个评分版本固定：需求来源版本、分析版本、评分规则版本、AI 提示词/模型版本（AI 建议时）、操作者/时间和完整输入快照。
- 历史版本只读；已发布规则不静默回算旧评分。旧版 v1 高/中/低求和规则生成的优先级继续按原分析版本展示，不因 v2 发布而改变。

#### 4.2.7 UI 与数据展示

**信息架构**

详情页顶部是需求摘要卡，之后是一个整合的“AI 评分与优先级”区域；不再把评分和 AI 分析拆成两个并列区块。

- **摘要卡**：最顶部是“返回需求池”，其下依次是标题/平台 ID、评分与优先级主视觉、负责人和流程状态、操作按钮。评分主视觉显示当前有效综合分（保留两位小数）、P0–P3 和评分置信度；没有评分时显示“暂无评分 / 评分待生成”，不伪造 0 分或 P。
  - 摘要卡只读取当前有效评分（`current`）；若只有 AI 新建议而没有当前值，显示“AI 建议 15.20 · P2”，点击进入评分区查看/采用，不把建议写成正式当前分。
  - 返回按钮在卡片最顶部，不放在标题右侧或内容区中部；移动端同样保持首屏可见。
- **AI 评分与优先级区域**：标题下首先是综合分/P 主视觉和评分版本状态，然后是 U/M/S/C 四维评分卡、九项输入表和 AI 分析建议；完整的 AI 说明、证据、假设和缺失信息作为该区域的次级内容展示。
  - U/M/S/C 四张维度卡分别显示该维度的合成值（U = 痛点×频次；M = 卖点×竞品；S = Roadmap×依赖；C = 三项成本最大值）、对综合分的贡献/含义，以及 AI 对该维度的建议、理由、证据或“需要补充”标记。
  - 九项输入表显示 AI 建议值、当前值、每项依据/假设；PM 编辑、保存、取消、采用 AI 建议和历史入口均在此区域内。
  - 模块、类型、适用人群和整体置信度作为“其他 AI 建议”展示；不得再出现第二个独立的“AI 分析与建议”大区块，避免同一分析内容重复出现。
  - 无评分/旧分析时，仍显示现有 AI 定性建议，并在评分位置提供“手动填写评分/重新分析”入口；规则未发布或评分失败时显示明确状态，不阻断详情其他部分。
- **适用人群**：放在 AI 评分与优先级区域内，靠近 AI 人群建议；AI 建议和 PM 当前标签分开显示。未确认时默认选中首个 AI 建议（见 §4.4），PM 修改后点击“保存人群标签”才生效。Beta 分析入口保留为次级入口，不抢占评分主视觉。

**验收与交互要求**

- 摘要卡必须在首屏显示综合分和 P；无评分时显示空状态，不得用旧版分析的自报 P 冒充当前评分。
- U/M/S/C 四维、九项输入、综合分和 P 的数值必须来自服务端当前评分版本；公式只读。
- 评分与 AI 建议只保留一个区域标题；移动端维度卡纵向排列，九项输入表可横向滚动。
- 评分编辑保存后摘要卡和评分区同时刷新；若版本冲突，摘要卡保留旧值并提示刷新，不显示未确认的新分。
- 所有空/失败/规则未发布状态沿用 §4.2.8；视觉上评分是主信息，AI 其他建议和证据是辅助信息。

#### 4.2.8 安全、异常与边界

- **安全标记**：AI 可基于原文标记安全相关；PM 可在评分编辑中修正并填写理由。安全标记只触发“安全复核”提示，不自动把 P 改为 P0，也不绕过公式；复核人应确认是否提高单项分数/α 或转人工决策。
- **缺失/假设**：某项无证据时仍可评分，但必须有假设说明和低置信度标记；若 AI 无法生成合法评分对象，整条评分进入可重试失败，主流程继续。
- **规则未发布**：沿用既有规则未发布语义，优先级留空并显示“待校准”；不得用 RICE/Kano 或模型自报 P 填充。
- **并发**：同一评分版本并发保存只能有一个成功；冲突必须提示并保留用户输入。
- **不可用**：AI 超时/限流/非法输出、数据库版本冲突、规则缺失都不能导致主需求详情不可打开；降级展示上一有效评分或“评分待重试”。

#### 4.2.9 与 Beta 分析的关系

- Kano 仍只在 Beta 手动运行，输出定性假设；没有合格样本时显示“未评”，不进入综合分。
- RICE 仍只在 Beta 手动保存草稿/计算，不参与 U/M/S/C、综合分或 P0–P3。
- Beta 结果不能覆盖评分当前值，也不能触发主评分重算或 Base 推送。

### 4.3 RICE 手动评分（Beta）

RICE 位于需求详情的次级“Beta 分析”入口，仅在用户主动打开并填写时运行。它不出现在默认需求池主流程，不自动触发，也不用于 U/M/S/C 或 P0–P3 计算。需求负责人负责录入并确认四项输入，AI 不自动填写或覆盖人工最终值：

| 字段 | 含义 | 输入责任 | 约束 |
|---|---|---|---|
| Reach | 在约定周期内受影响的用户数或事件数 | 需求负责人 | 周期和计量单位需在产品组统一配置；允许填写依据说明 |
| Impact | 对单个受影响用户或既定目标的影响程度 | 需求负责人 | 使用产品组配置的离散等级和对应分值 |
| Confidence | 对 Reach、Impact、Effort 估算的把握程度 | 需求负责人 | 使用产品组配置的百分比或离散档位，并填写依据 |
| Effort | 完成需求所需的整体投入 | 需求负责人 | 使用产品组统一的人月/人周/人日单位；范围可包含相关产品、设计、研发与测试投入 |

**计算规则**：`RICE = Reach × Impact × Confidence ÷ Effort`。Confidence 若以百分比输入，计算时转换为 0–1。Effort 必须大于 0；任一字段缺失、无效或 Effort 为 0 时，不计算分数，展示“待补充”。

**人工责任与历史**：记录录入人、最后修改人、时间和字段变更前后值。AI 可提示缺项、解释公式或协助整理估算依据；不得将 AI 推算值写成负责人已确认的 RICE 输入。

**待产品组配置**：Impact 档位及映射分值、Confidence 档位/百分比、Reach 周期与单位、Effort 单位。配置确定前，Beta 仅可保存草稿输入，不展示跨需求正式排名。该配置不影响主流程优先级。

### 4.4 六层用户人群建议与人工修改

- AI 对每条需求输出 0 个或多个建议层级，并为每个建议附理由和证据；该标签作为主流程的非阻断上下文，不等于 Kano 结论。不得因材料中“未提到”就推断该人群不适用。
- **默认选择**：当 PM 尚未确认人群（`confirmed=false`）、且 AI 至少给出一个层级时，UI 默认选中 AI 输出顺序中的第一个建议层级，作为未保存的编辑草稿；不自动写入 PM 确认值，也不把 AI 建议伪装成人工结论。AI 有多个建议时用户可继续多选；AI 没有建议时不默认选择。若 PM 已确认过（包括确认空集），刷新详情不得恢复默认选择或覆盖 PM 当前值。
- PM 可以在需求详情中添加、取消或替换 L1–L6 标签，允许多个层级并存；修改后必须点击“保存人群标签”才生效，保存不触发分析、推送或通知。
- 视觉区分：AI 建议使用带“AI 建议”标识的浅色/虚线建议标签；PM 可点击的标签使用独立的选择样式（选中态与未选中态明确）；“保存人群标签”是独立的主按钮，不能与标签采用同一外观。AI 建议、PM 未保存选择、PM 已确认值三者不得混淆。
- 同时保存 AI 建议和 PM 当前标签，人工修改不得覆盖或伪装成 AI 结果。
- 若证据不足，显示“待判断”，并指出需要补充的人群信息。
- 人群修改记录操作者、时间及变更前后值。

### 4.5 Kano AI 假设（Beta）

Kano 仅由用户在 Beta 入口手动触发，不作为同步后的自动分析步骤，不产生或调整 P0–P3，也不阻断需求推送。首期输出仅为基于访谈总结和当前需求的定性研究假设。

#### 输入

- 当前需求的标题、描述及批准进入 AI 的非个人业务上下文。
- 当前需求的人群标签及其确认状态。
- 已批准的、去标识化的访谈总结及来源章节/链接。

姓名、手机号、邮箱、用户 ID、未批准的原始个人信息和附件原文不得发送给模型。访谈总结若包含可识别个人信息，应先清理或遮蔽。

#### 问卷模板

对每个需求能力点，按目标人群分别生成一组 Kano 成对问题：

1. **功能正向题**：“如果产品具备【能力】，且体验达到【可理解的质量描述】，你的感受是？”
2. **功能反向题**：“如果产品不具备【能力】（或无法提供该体验），你的感受是？”

每题选项：喜欢、理所当然、无所谓、可以接受、不喜欢。问题需使用具体能力和场景，避免把多个功能合并成一个宽泛问题。

本轮允许 AI 基于访谈总结推演虚拟画像的可能回答倾向，用于形成研究假设；推演结果不得生成虚构的受访者记录、样本数、百分比、显著性或 Kano 系数。

#### 输出

| 字段 | 说明 |
|---|---|
| Kano 候选类型 | 基本型、期望型、一维质量、魅力型、无差异型、反向型、证据不足；术语可由产品组统一 |
| 适用人群 | 一个或多个 L1–L6；证据不足时为待判断 |
| 解释 | 说明能力存在/缺失对该人群满意度的推测影响 |
| 证据 | 访谈总结中的摘要事实或原文片段，并附文档链接和章节/主题 |
| 置信度 | 高/中/低的定性判断，解释证据覆盖和不确定性；不是统计置信区间 |
| 研究状态 | AI 假设（待验证）/ PM 已复核 / 已有真实 Kano 问卷验证 |
| 缺口 | 未覆盖人群、冲突证据、缺失样本或需要进一步询问的问题 |

访谈推演始终标记“AI 假设（待验证）”。真实问卷数据只有在采集实际配对回答后，才可进入统计归类；不得用虚拟回答替代真实回答。

### 4.6 访谈材料与证据管理（Beta）

- 访谈总结作为可版本化的 AI 参考材料，至少包含人群/产品线（已知时）、场景、需求或痛点、访谈时间（已知时）和来源链接。
- 不要求来源总结提供无法确认的字段；缺失字段明确标为未知。
- 分析结果引用具体来源材料和主题，支持 PM 回到原文核对。
- 更新访谈材料或需求内容后，新的 AI 分析生成新版本；历史分析保留，不静默覆盖。

### 4.6 总览页优先级分级统计

- 总览页新增“优先级分级”区域，显示 P0、P1、P2、P3 的需求数量，以及“待评分”数量；统计口径为全量业务需求，合成验收数据不计入。
- 分级取数优先级：
  1. 当前有效评分版本（`current/confirmed`）的 P0–P3；
  2. 没有评分、但最近一次已分析版本有历史优先级的，使用该历史优先级，并在界面标注“历史分析优先级（v1）”，不套用 v2 分数范围；
  3. 两者都没有的计入“待评分”，不得用 0 分或模型自报 P 补齐。
- 区域需展示当前已发布评分规则及范围：P0 ≥45、P1 25–44.99、P2 10–24.99、P3 <10；规则未发布时明确提示，不用其他规则替代。分数以服务端评分版本为准。
- 统计区应同时显示已分级/待评分数量和“其中历史优先级 X 条”，让用户理解为什么分级数量总和与总需求数可能不同；点击“查看需求池”进入需求池。
- 该统计只读，不改变任何需求状态或优先级；刷新总览时随指标 API 更新。


### 4.7 重复需求处理（P1，2026-10-29 新增）

#### 4.7.1 目标与原则

- **目标：避免重复处理。** 同一问题被多次提交、或历史需求被重复导入时，不应重复执行 AI 分析、负责人分配、Base 推送和飞书通知。
- **判定与记录生命周期解耦。** 判定按来源稳定身份持久保存，不依赖应用内需求行是否存在；删除应用记录或 TB 重推不能使已确认的判定失效。
- **只有人工确认才压制。** 系统提示的“疑似重复”只做提示，不隐藏、不压制；压制必须由 PM Leader / 指定操作人显式确认，且可撤销。
- **单一事实源。** 需求是否被压制统一由决策派生，同步与分析/推送链路都读取同一状态，不允许各处理分支各自推断。

#### 4.7.2 判定对象与身份

- P1 覆盖 **TB 来源**需求：决策以 `(来源配置 ID, TB 需求 ID)` 为稳定键保存，应用内删除记录、TB 全量或增量重同步、记录重新导入后，同一 TB 需求再次出现时自动继承已确认判定。
- `web_manual` 来源在本轮不落决策（无 TB 需求 ID）；后续版本再定义手工需求的稳定身份。
- 同标题提示仍可自动刷新（仅提示），但**不得覆盖人工确认的判定**。

#### 4.7.3 判定动作

PM Leader / 指定操作人可在需求详情执行：

| 动作 | 语义 | 处理结果 |
|---|---|---|
| 确认重复 | 指定一条主记录（canonical），本条为副本 | 本条压制：不分析、不推送、不通知；主记录正常流转 |
| 忽略 | 本条不进入当前处理池，但保留可追溯记录 | 本条压制 |
| 确认非重复 | 撤销疑似提示，明确保留独立处理 | 恢复 active |
| 撤销判定 | 删除已确认的判定 | 恢复 active，回到正常链路 |

- 判定写入带乐观版本号：版本冲突返回 409，不覆盖他人判定；记录操作者、时间、理由，并产生审计事件（确认/复核/撤销）。
- 一次操作只能有一个有效判定；重复提交幂等。

#### 4.7.4 处理链路压制

- 已确认重复/忽略的需求：不进入 AI 分析队列、不进入 Base 推送队列、不生成通知事件；已排队或执行中的作业在处理器入口二次校验并跳过。
- 列表默认视图不展示已压制需求；统计口径单列“已压制”，不计入待处理/待推送等默认工作队列。
- 压制为可逆状态：撤销后回到 active，由正常同步/分析/推送链路继续处理；不要求人工补数据。
- 已推送过 Base 的重复行**不得删除**（避免丢失 PM 在 Base 的处理数据）；P1 先保证不再产生新推送与新通知，Base 行的重复标记与停止通知在后续版本补齐。

#### 4.7.5 Web 展示与交互

- 需求池提供处理状态视图：**全部 / 仅活跃 / 已压制**；切换立即生效并重置分页。
- 列表行展示“疑似重复”“已压制（重复/忽略）”标识；已压制行视觉弱化但仍可打开详情。
- 详情展示当前判定与主记录链接；提供确认重复（选择主记录）/确认非重复/忽略/撤销动作；409 冲突提示刷新后重试。
- 详情需明确提示已压制需求“不会进入 AI 分析、Base 推送与通知”。

#### 4.7.6 边界与非目标（后续版本）

- 指纹兜底（TB 删除后重建、拿到新 TB ID、跨项目同需求）——P2。
- 已推送 Base 重复行的标记与停止后续通知——P2。
- 判定后需求实质内容变化的“待复核”自动流转——P2。
- 独立“重复审查”列表页与批量操作——P3；P1 用需求池筛选视图承载。
- 自动合并/自动删除需求记录不做；判定只影响后续处理，不物理删除事实记录。

### 4.8 加载与刷新体验（非功能性要求，2026-10-29 新增）

- **首屏骨架屏。** 首次加载且无旧数据时，总览统计/优先级/待办/最近同步、需求池列表、需求详情及同步记录、团队、模块、审计等面板显示结构化骨架屏，不使用空白或纯文字占位导致布局跳动；骨架屏对辅助技术标注加载状态，并尊重系统“减少动态效果”设置。
- **静默刷新。** 已有数据时的刷新（轮询、操作后回写、手动刷新）保留现有内容，不清空、不闪回骨架屏；详情操作成功后只就地更新详情与对应列表行。
- **局部刷新。** 批次运行中的进度轮询只更新批次数据；批次进入终态或用户手动刷新时才触发一次全量静默刷新。同步提交后不整页重载。
- **请求竞态保护。** 快速切换筛选/视图时，后发请求优先；过期响应不得覆盖新结果。
- **失败可恢复。** 局部刷新失败保留旧数据并提示可重试，不把整页变成错误态。
- **不改变数据边界。** 加载优化不新增数据展示口径；Web 仍不回读 Base PM 处理状态与通知送达状态。

### 4.9 需求池来源区分（2026-11-19 新增）

> 目标：在一个需求池内，把 Teambition、多维表格、手工、聊天粘贴四种来源**明显地区分**出来；不拆池、不改主流程、不加迁移。
> 背景：5c-1 已提供来源徽标和下拉筛选，但下拉藏在「更多筛选」里，默认来源 TB 占绝大多数（当前 332/333），灰色小徽标在列表中几乎抓不住。用户 2026-11-19 确认按本节方案实施。

#### 4.9.1 产品原则

- **单池，不拆三个池**：需求池仍是「今天该做什么」的唯一队列；P0 的 TB 需求与 P0 的收集表需求必须同屏可比，重复判定也依赖单池。
- **来源是一等维度，不是新流程**：来源只影响「怎么来的」展示、列表筛选和计数；不改变 AI 分析、优先级、负责人映射、Base 推送和通知。
- **只加不改**：新增计数接口和来源展示层；现有 `?source=` 筛选、导出、分页、深链、创建/编辑/推送/通知行为保持不变；不加数据库迁移、不改 Base 字段。
- **默认来源降噪**：TB 是绝大多数，列表行不挂徽标、不挂色条；只有非默认来源（多维表格 / 手工 / 聊天粘贴）做视觉标记。
- **不为来源拆导航**：侧边栏不加三个池的菜单项；来源切换在需求池内部完成。

#### 4.9.2 需求池来源 Tab

**位置与顺序**：需求池顶部、列表之上，固定顺序：

`全部来源`｜`Teambition`｜`多维表格`｜`手工`｜`聊天粘贴`

> Tab 文案用「全部来源」，与现有下拉一致，也避免和顶部处理视图的「全部」重名；如坚持用「全部」，需在两个控件上做视觉区分。

| Tab 文案 | `source` 参数 | 判定 | Base「来源方式」 |
|---|---|---|---|
| 全部来源 | 空 | 不加来源条件 | — |
| Teambition | `teambition` | `source_type='teambition'` | Teambition |
| 多维表格 | `base_form` | `source_type='base_form'` | 多维表格 |
| 手工 | `web_manual` | `source_type='web_manual'` 且 `intakeOrigin` 不为 `chat_paste` | Web 手工 |
| 聊天粘贴 | `chat_paste` | `source_type='web_manual'` 且 `intakeOrigin='chat_paste'` | 聊天粘贴 |

- 默认选中「全部来源」；无 `source` 参数或参数为空都按「全部来源」处理。
- Tab 是来源筛选的唯一控件；选中态用文字/下划线/背景等非仅颜色的信号。
- 点击 Tab 切换列表筛选；切换后分页回到第一页（沿用现有筛选变更行为）。
- 与现有 URL 参数 `source` 同源：`source=teambition|web_manual|base_form|chat_paste`；Tab 点击复用现有筛选的 URL 同步逻辑（不新增路由、不改变 history 模式），刷新、复制链接能恢复同一视图；浏览器前进/后退行为与现有筛选一致。
- 无效的 `source` 值按现有后端校验处理，不把页面变成错误态；前端回退「全部来源」。

**计数**：

- 每个 Tab 显示当前来源的活跃需求数；来源键与接口字段一一对应：`teambition`、`web_manual`、`base_form`、`chat_paste`，`all` 对应「全部来源」。
- 计数口径固定为**仅活跃**（`processing_state='active'`），与需求池默认「仅活跃」视图一致；已压制重复/忽略不计入。
- 计数是**活跃范围内的总数**，不随搜索、负责人、同步/分析/推送状态、优先级、分页变化；只随数据变更后的刷新变化。这是「来源分布」口径，不是当前筛选结果数；如需按当前筛选联动，另立需求并扩展接口参数。
- 计数为 0 时显示 `0`，不隐藏 Tab。
- **计数获取失败**（超时、503、响应缺字段）：隐藏所有计数，Tab 标签和筛选照常可用，列表不受影响；不显示 0、不弹阻塞错误、不把整页变错误态；下一次刷新重试。
- **处理视图联动**：用户把顶部处理视图切到「全部」或「已压制重复」时，Tab 隐藏计数（只显示标签），避免「计数是活跃数、列表行数更多」的误读；切回「仅活跃」恢复计数。来源筛选在三种视图下都可用。
- 计数不单独轮询；随列表加载/刷新或数据变更后的既有刷新一起请求。

**删除旧下拉**：

- 删除「更多筛选」里的「来源」下拉；Tab 完全替代它。
- 「更多筛选」的其他筛选项、已生效筛选计数、清除筛选行为保持不变；来源不再计入「更多筛选」的计数徽标。

**导出**：

- CSV 导出沿用当前筛选（含 `source`），行与列不变；不新增 `intakeOrigin` 列（该 OBS 另立需求）。
- 导出入口位置、文件名规则、列顺序不变。

#### 4.9.3 列表行视觉

| 来源 | 行首色条 | 徽标 | 示例 |
|---|---|---|---|
| Teambition | 无 | 无（默认来源） | 不挂任何来源标记 |
| 多维表格 | 3px，蓝色 | `多维表格·<渠道>` | `多维表格·销售` |

- 渠道为空时只显示来源名（如 `多维表格`），不显示 `·null`、`·undefined` 或空括号。
- 色条贴在行首，不改变行高、缩进和对齐；长渠道文本截断并提供完整 `title`/悬浮提示，不能把标题挤到换行。
- 颜色不是唯一信号：徽标文字必须始终存在；色条只做扫视辅助。色值使用项目现有 Arco/CSS token，新增三个语义变量（多维表格/手工/聊天粘贴），满足对比度要求。
- 现有 5c-1 徽标文本（手工/聊天粘贴/多维表格）保留，增加渠道后缀和色条；TB 继续不挂徽标。
- 移动端/窄屏：徽标可截断，但来源名不能被截掉；不允许横向溢出。

需求详情底部新增只读区块：

**同页「需求信息」字段（2026-11-19 补充）**

- 5a.1 之前通过聊天粘贴创建、但没有 `intakeOrigin` 留痕的历史行，按「手工」展示；不伪造「聊天粘贴」，不回溯改数据。

- **详情「编辑需求」入口（2026-11-20 口径，本轮实现）**：

  - 界面固定提示：「修改只保存在需求平台，不会写回多维表格收集表。」
  - 创建时间口径：详情「创建时间」取服务端 `requirements.created_at`（平台收录时间），四种来源一致；不取收集表行的提交时间，后者不在详情展示。

#### 4.9.5 计数接口

`GET /api/requirements/source-counts`

- 鉴权：与需求列表一致，登录租户用户可用；不新增权限矩阵。
- 除 §4.12 新增的可选 `pool=product|group`（缺省 `product`）外，无查询参数；固定统计 `processing_state='active'` 的需求，不应用搜索/负责人/状态/优先级筛选，不含已压制重复/忽略。
- 成功响应 `200`：

```json
{"counts":{"teambition":332,"web_manual":1,"base_form":0,"chat_paste":0,"all":333}}
```

- 口径：
  - `teambition`：`source_type='teambition'`
  - `web_manual`：`source_type='web_manual'` 且 `source_payload->>'intakeOrigin'` 不等于 `chat_paste`（含空值）
  - `chat_paste`：`source_type='web_manual'` 且 `source_payload->>'intakeOrigin'='chat_paste'`
  - `base_form`：`source_type='base_form'`
  - `all`：全部活跃需求，不按来源过滤；当前等于四项之和，未来新增来源类型只计入 `all`，不新增未定义的键
- 五个键**始终存在**，值为整数且 ≥0，不用 `null` 表示 0。
- 失败：数据库/依赖不可用返回 `503 DEPENDENCY_UNAVAILABLE`；前端按 4.9.2 隐藏计数。读接口不写审计、不加迁移。
- 性能：一条 `GROUP BY`/条件聚合 SQL，不逐来源查询；当前 333 条量级目标 <300ms（目标环境记录实际值）；本轮不加索引。
- 实现注意：路由必须排在 `GET /api/requirements/:id` 之前匹配，避免被当作需求 ID；openapi 同步新增该路径与响应 schema。

#### 4.9.6 边界与非目标

- 不拆 Teambition / 多维表格 / 手工三个需求池；不加侧边栏菜单。
- 不新增来源类型，不改 `source_type` 枚举，不加迁移。
- 不改 AI 分析、优先级、负责人映射、Base 推送、通知和 Base 字段。
- 不改导出列、分页契约、现有 `?source=` 参数语义；来源 Tab 只是把同一状态显性化。
- 不做按来源的权限、通知、采纳率报表或独立统计页。
- **非 Teambition 来源的重复提示（2026-11-20 口径，下一轮）**：自动 same-title「疑似重复」与确认压制仍只覆盖 Teambition；手工/聊天粘贴在提交前展示最多 5 条相似需求（标题 / 平台 ID / 来源，可点开，不阻断），多维表格收录后在详情只读展示相似需求；非 TB 不自动写 `duplicate_of`、不自动压制、不写 Base、不发通知。确认重复若扩展到非 TB，另立迁移/接口，以 `requirements.id` 为稳定键，必须人工确认，不按标题自动确认。细则与验收判据见 §4.9.9。

#### 4.9.9 非 Teambition 来源的重复边界与相似需求提示（2026-11-20，下一轮）

> 目的：非 TB 来源不再出现无效的「重复处理」按钮；新建/收录时给只读的相似提示，帮助 PM 自查，但不改变任何处理状态、不阻断提交。

**A. 非 TB 详情隐藏「重复处理」**
- `base_form` / 手工 / 聊天粘贴详情不渲染「重复处理」区块（标题、状态、确认重复、确认非重复、忽略、撤销全部不出现），也不发起 `PUT/DELETE /api/requirements/:id/duplicate-decision`。
- 不改变 `processing_state`、`duplicate_of`、Base 重复标记或通知；历史数据里如已有疑似重复提示，只隐藏入口，不改数据。
- Teambition 详情保持原样：重复处理区块、疑似重复提示、8 个 TB 字段和判定入口都不变。

**B. 手工 / 聊天粘贴新建表单的相似需求**
- 位置：标题字段下方；聊天粘贴草稿生成后立即按草稿标题用 `GET` 查一次（草稿返回的 `similar` 只作为即时判断，不直接展示来源名）；用户改写标题失焦后重查。
- 触发：标题失焦（含点击提交导致的失焦）且 trim 后 ≥2 字，查一次；若提交时尚未查询，可并行触发但不等待；同一标题不重复请求；标题变化后才重查；查询中不显示 loading、不禁用提交。
- 接口：`GET /api/requirements?q=<标题>&limit=5&processingState=active`；不新增端点、不调用模型。
- 展示：最多 5 条，按接口返回顺序（创建时间倒序，新→旧）；每条显示「平台 ID · 标题 · 来源名」；来源名与列表一致（聊天粘贴按 `source.intakeOrigin=chat_paste` 判定）；不展示状态、负责人、PM 字段。
- 文案：「相似需求（按标题关键字匹配，仅供参考，不代表重复；不会阻断提交）」。
- 空态/失败：0 条时整块不渲染；查询超时（前端 2s）、4xx/5xx、无权限、网络错误一律静默隐藏，不弹错、不重试、不影响提交；旧请求迟到不得覆盖当前标题结果。
- 点击：新标签页打开 `?requirement=<id>`；不关闭、不重置当前表单。
- 不阻断：不得禁用/延迟提交按钮，不得自动选中、自动合并、自动填表，不得改标题/描述，不得写 `duplicate_of` / `processing_state` / Base / 通知 / 审计；提交不等相似查询结果。

**C. 多维表格详情的相似需求**
- 位置：`base_form` 详情「需求信息」之后、AI 分析之前，独立只读块「相似需求（只读，仅供参考）」。
- 查询分两段（仅详情块；新建表单不做前缀降级），每次渲染最多 2 次请求：
  1. 先用整条标题查；排除当前需求自身后若有结果，直接展示。
  2. 若整条标题 0 条且标题（trim 后）超过 8 个字：若 trim 后标题以 `【…】` 开头，先去掉该前缀并 trim，再取前 8 个字（不足 8 取全部；少于 2 字不查）查第二次；仍 0 条则整块不渲染。
- 每段请求 2s 超时；第一段超时/失败直接隐藏，不再发第二段；第二段超时/失败也隐藏。两段都只用 `limit=5&processingState=active`，排除自身，排序、展示、点击与 B 相同。
- 说明：整标题子串匹配对长标题几乎恒为空，这是补偿规则，不改变「仅供参考、不阻断」的定位，也不改搜索接口语义。
- 手工/聊天粘贴详情不新增该块（创建时已提示）；TB 详情不新增（已有 TB 疑似重复机制）。

### 4.10 需求评估与 Investigation 提示词（2026-11-20 新增）

> 目标：在现有 AI 分析（把需求读准）之上，增加一层「值不值得做、做不做得成」的**按需**评估；一次生成评估结论和 Investigation 提示词，PM 复制提示词到自己的 Agent 继续调查和写 PRD。
> 已定口径（用户 2026-11-20 确认）：按需生成、独立新表落库、不写 Base、Investigation 提示词只复制走；不改 `requirements` 表、不自动跑、不替代 PM 决策。

#### 4.10.1 产品原则

- **按需，不自动**：只在详情页点「生成评估」时调用模型；不在需求创建、编辑、分析完成时自动触发，不批量跑。不是所有需求都值得花一次模型调用。
- **链路位置**：需求收集（现有）→ AI 初步分析（现有，读准事实）→ **本节需求评估**（值不值得做/做不做得成）→ Investigation 提示词（复制走）→ PM 在自己的 Agent 写 PRD。本节不重做初步分析，也不替代 PRD。
- **建议不是结论**：界面固定标注「AI 建议，非结论」；评估用于 PM 评审和调查准备，不替代 PM 决策，不给排期/人力承诺。
- **不改需求本体**：补充的背景/目标/场景只写新表，不写 `requirements`，不写 Base，不发通知；需求详情其它区块和现有 AI 分析不变。
- **版本化可追溯**：每次生成一条新版本，不覆盖历史；失败也留 `failed` 版本，便于复盘和重试。
- **专业口径同源**：服务端 prompt 以版本化 skill 文件为唯一口径源（`skills/requirement-assessment/SKILL.md`，`rq-assessment-v1`），按固件/软件产品经理的思考框架输出；不得在服务端另写一套规则。
- **一次调用产出两件**：同一次模型调用同时生成评估结论和 Investigation 提示词，避免两次调用结论不一致；UI 分两块展示，提示词可折叠、一键复制。不单独设「生成提示词」按钮；重新生成会同时更新评估和提示词。
- **复制走**：Investigation 提示词只提供复制，由 PM 带去自己的 Agent；本期不直接发起后台调查、不自动写 PRD。

#### 4.10.2 用户流程

1. 打开需求详情 → 「需求评估」块；默认不调用模型，展示空态或最新历史版本。
2. 可选补充「需求背景 / 目标 / 使用场景」；三项都可留空。
3. 点「生成评估」；服务端一次调用生成评估 + Investigation 提示词，写入新版本。
4. 详情展示：结论（建议推进/建议暂缓/需要调查）、置信度、背景/目标/范围/业务价值/可行性/结论理由/假设/待确认问题；Investigation 提示词折叠展示，可复制。
5. 修改补充内容后可「重新生成」→ 新版本；历史版本可切换查看，旧版本不可改；切到历史版本时，补充输入框回填该版本的背景/目标/场景，可改后重新生成。
6. 失败：显示错误和重试入口；失败版本可在版本历史看到，不覆盖旧版本。

入口只在需求详情；不加侧边栏菜单、不做独立评估页、不自动批量生成。

#### 4.10.3 补充输入

| 字段 | 必填 | 上限 | 说明 |
|---|---|---:|---|
| `background` 需求背景 | 否 | 2,000 字 | 为什么现在做、业务/用户上下文、已有反馈或数据 |
| `goal` 目标 | 否 | 1,000 字 | 希望达成的用户/业务目标，尽量可衡量 |
| `scenario` 使用场景 | 否 | 2,000 字 | 谁在什么场景使用、关键旅程、边界条件 |

- 三项都可为空；全空也允许生成，但结果应更多落到 `investigate` / `openQuestions`，不得硬编背景或目标。
- 输入写入评估表 `inputs`（三个键，空字符串保留），用于版本追溯；**不写需求本体**。
- 发送模型前复用现有 PII 掩码；界面提示「不要粘贴客户姓名、电话、邮箱、订单号、密钥」。输入会落库，PM 需自行避免不必要的个人信息。
- 提出人只做界面展示，**不进入模型**；模型也不得在输出里猜/补提出人。
- 输入超长/格式错误返回 400，不创建版本；空输入不是错误。

#### 4.10.4 输出契约 v1（最终措辞）

模型只输出一个 JSON 对象，不要 Markdown 代码块、不要解释文字、不要额外字段：

```json
{
  "background": "string",
  "goal": "string",
  "scope": { "in": ["string"], "out": ["string"] },
  "value": "string",
  "feasibility": {
    "technical": "string",
    "cost": "string",
    "dependency": "string",
    "risk": "string"
  },
  "verdict": "advance",
  "verdictReason": "string",
  "confidence": "medium",
  "assumptions": ["string"],
  "openQuestions": ["string"],
  "investigationPrompt": "string"
}
```

字段语义与校验：

| 字段 | 语义 | 校验 |
|---|---|---|
| `background` | 基于需求事实 + PM 补充，重述「为什么现在做」；不是原文复制，不编造 | 非空，≤2,000 字 |
| `goal` | 用户/业务目标，尽量可衡量；区分目标与方案 | 非空，≤1,000 字 |
| `scope.in` | 这次要做什么、MVP 边界 | 1–8 条，每条 ≤200 字 |
| `scope.out` | 明确不做什么 | 0–8 条，每条 ≤200 字；没有边界可空并在 `openQuestions` 追问 |
| `value` | 业务价值 + 用户价值，写清受益者和依据；不只写「提升体验」 | 非空，≤2,000 字 |
| `feasibility.technical` | 技术可行性：固件/硬件/功耗/传感器/协议/App/云/认证 | 非空，≤2,000 字；写依据与不确定性 |
| `feasibility.cost` | 成本量级：研发/测试/认证/物料/供应链/售后 | 同上 |
| `feasibility.dependency` | 关键依赖：芯片/供应商/平台/法规/外部团队 | 同上 |
| `feasibility.risk` | 安全/合规/质量/进度/口碑风险及缓解方向 | 同上 |
| `verdict` | `advance` / `hold` / `investigate` 三选一 | 严格枚举 |
| `verdictReason` | 最关键理由 + 最大不确定性；不复述全文 | 非空，≤1,000 字 |
| `confidence` | `high` / `medium` / `low` | 严格枚举 |
| `assumptions` | 本次用到的推断/假设；每条以「假设：」开头，写清影响哪个判断 | 0–8 条，每条 ≤300 字 |
| `openQuestions` | 需要 PM 补充或调查确认的具体问题，不用「补充更多信息」 | 0–8 条，每条 ≤300 字 |
| `investigationPrompt` | 可直接复制的中文调查提示词，要求见下方「Investigation 提示词要求」/ skill §8 | 100–5,000 字；建议 600–1,200 字 |

- 所有字段必填；字符串非空；`scope.out`、`assumptions`、`openQuestions` 可为空数组；不用 `null`。
- 信息不足时，字段可以写「依据不足：…」并放入 `openQuestions`；不得用编造内容填满，也不得因为缺信息就省略必填字段。
- 不接受额外字段；输出不合规按失败处理，不返回半成品。
- 模型输出不得包含 PII、密钥、内部链接、Base 表 ID/record ID；不得包含排期/人力承诺。
- 一次模型调用同时产出评估和提示词；不做第二次「生成提示词」调用。

**三档结论判定标准**：

| 结论 | 判定（主要满足） | 反例 |
|---|---|---|
| `advance` 建议推进 | 问题真实且频次/影响足够；用户价值或业务价值至少一项明确；范围能在当前版本收敛；关键可行性无致命未知；风险可接受；有明确下一步（PRD/评审/预研结论） | 只因「用户说了」；价值靠想象；关键技术/成本/合规未知；范围明显失控 |
| `hold` 建议暂缓 | 当前不做更好：价值不足、优先级低、与战略/路线冲突、成本/风险明显不划算，或已有更优替代；必须写重评触发条件 | 还有会改变结论的关键未知（应 `investigate`）；只是暂时没资源但价值明确 |
| `investigate` 需要调查 | 存在会改变结论的关键未知：用户规模/频次、真实场景、技术可行性、成本量级、认证/合规、供应商依赖、竞品事实；必须给调查问题/证据来源/时间盒 | 把「不知道」写成 `advance`；用常规信息收集拖延 |

- 信息严重缺失：默认 `investigate`，不得 `advance`；明确没有业务价值才可 `hold`。
- 技术不可行且无法绕开：`hold`；只是不确定能不能做：`investigate`。
- 价值存疑但可通过调查回答：`investigate`；战略明确不做：`hold`。
- `advance` 不等于排期承诺；`hold` 必须写重评触发条件；`investigate` 必须能回答「查什么、怎么查、多久」。
- `confidence`：`high`=关键事实有输入证据、无重大未知；`medium`=部分推断/需 PM 补充；`low`=关键输入缺失或冲突。`confidence` 与 `verdict` 独立（可以 `investigate + high`）。

**Investigation 提示词要求**：必须包含 ① 背景（需求是什么/为什么评估/已有事实）② 目标（1–3 个决策问题）③ 待验证假设（假设不成立时结论怎么变）④ 目标用户/样本与招募渠道 ⑤ 开放式、不诱导的问题 ⑥ 要收的证据与最低数量 ⑦ 产出物（调查纪要/证据清单/PRD 章节）⑧ 时间盒与判定标准（什么结果支持 advance/hold/investigate）⑨ 约束（不预设答案、不以「用户说想要」为唯一证据、不收集不必要 PII）。中文、结构化小标题、可直接复制、建议 600–1,200 字。

#### 4.10.5 存储：`requirement_assessments`（迁移 0030）

只新增表，不改 `requirements`、不改 Base：

| 列 | 类型 | 约束 |
|---|---|---|
| `id` | uuid | 主键，应用生成 |
| `requirement_id` | uuid | 非空，外键 `requirements(id) ON DELETE CASCADE` |
| `version` | integer | 非空，同一需求从 1 递增；唯一键 `(requirement_id, version)` |
| `status` | text | 非空，`running` / `succeeded` / `failed`；`running` 只表示生成在途，不得作为成功展示 |
| `prompt_version` | text | 非空，本期 `rq-assessment-v1` |
| `model` | text | 生成成功/失败时记录实际模型 |
| `inputs` | jsonb | 非空，`{background, goal, scenario}`，空字符串保留 |
| `output` | jsonb | 成功时为契约对象；失败为 null |
| `error_code` | text | 失败时记录错误类（如 `rate_limited`/`timeout`/`analysis_failure`）；成功为 null |
| `created_by` | text | 非空，可信登录用户 |
| `created_at` | timestamptz | 非空，服务端时间 |
| `completed_at` | timestamptz | 可空；成功/失败完成时间，`running` 时为 null |

- 索引：主唯一键 + `(requirement_id, version DESC)` 供历史列表；无需额外索引。
- 版本分配在事务内按 `MAX(version)+1` 或唯一键重试，保证并发不冲突；旧版本不可覆盖。
- **running 不得永久卡住**：超过 2 分钟（2×默认 60s 超时）仍为 `running` 的版本，GET/启动恢复时标为 `failed`、`error_code='timeout'`，并允许重新生成；UI 不把 `running` 当成功。
- **同需求单飞**：POST 前检查该需求是否存在未超时的 `running` 版本；有则返回 `409 ASSESSMENT_IN_PROGRESS`，不调用模型、不新建版本；`running` 超时按上一条转 `failed` 后再允许。不同需求可以并行。
- 删除需求时评估行级联删除，不留孤儿；本期不提供评估删除接口，测试数据按 L 流程 SQL 清理。
- 评估表本身即追溯记录；本期不新增 `audit_events` 事件，不记模型正文/密钥。

#### 4.10.6 接口

**`POST /api/requirements/:id/assessments`**

- 鉴权：与需求详情一致，登录租户用户；不新增角色/权限。
- Body：`{ "background"?: string, "goal"?: string, "scenario"?: string }`，三项可选；上限见 §4.10.3。
- 成功 `201`：

```json
{
  "item": {
    "id": "uuid",
    "requirementId": "uuid",
    "version": 1,
    "status": "succeeded",
    "promptVersion": "rq-assessment-v1",
    "model": "deepseek-flash",
    "inputs": { "background": "...", "goal": "...", "scenario": "..." },
    "output": { "background": "...", "goal": "...", "scope": { "in": [], "out": [] }, "value": "...", "feasibility": { "technical": "...", "cost": "...", "dependency": "...", "risk": "..." }, "verdict": "advance", "verdictReason": "...", "confidence": "medium", "assumptions": [], "openQuestions": [], "investigationPrompt": "..." },
    "errorCode": null,
    "createdAt": "2026-11-20T02:00:00.000Z",
    "completedAt": "2026-11-20T02:00:45.000Z"
  }
}
```

- 一次请求只调用一次模型；不异步排队。前端在历史里存在 `running` 版本时每 5 秒静默刷新一次历史（仅 GET），用于跨标签页/超时后的状态回收，不是后台任务、不重复生成。
- 失败映射：

| 场景 | HTTP | 错误码 | 是否落 failed 版本 |
|---|---|---|---|
| 需求不存在 | 404 | `NOT_FOUND` | 否 |
| 输入超长/格式错误 | 400 | `VALIDATION_FAILED` | 否 |
| 同一需求已有未超时 `running` 版本 | 409 | `ASSESSMENT_IN_PROGRESS` | 否（不调用模型、不新建版本） |
| 每用户限流（默认 2 次/分钟、20 次/天） | 429 | `RATE_LIMITED` + `Retry-After` | 否（未调用模型） |
| 供应商 429 | 429 | `RATE_LIMITED` + `Retry-After` | 是，`rate_limited` |
| 供应商超时/网络/5xx | 503 | `DEPENDENCY_UNAVAILABLE` | 是，`timeout`/`network_error`/`provider_error` |
| 输出不合规 | 503 | `DEPENDENCY_UNAVAILABLE` | 是，`analysis_failure` |
| 鉴权/配置/请求错误 | 500 | `INTERNAL` | 是，`auth_error`/`request_error` |

- 失败版本 `output=null`，只存 `error_code` 和 `inputs`；不存供应商正文/密钥。
- 本期不做跨请求幂等键；同需求用 `running` 单飞（409），不同需求可并行；前端生成中仍禁用按钮，服务端单飞与限流双重兜底。
- 超时：评估专用 `ASSESSMENT_TIMEOUT_MS` 默认 **60,000ms**（不复用现有分析 20s 超时，避免长输出被掐断）；前端 65s 超时提示。
- 限流默认 2 次/分钟、20 次/天（进程内、多实例各自计数、重启归零），可按运营需要调配置；429 必须带 `Retry-After`。

**`GET /api/requirements/:id/assessments`**

- 返回 `{ "items": [ ... ] }`，按 `version DESC`；空历史返回 `items: []`。
- 列表项含 `id/version/status/promptVersion/model/inputs/output/errorCode/createdAt/completedAt`；`output` 只在成功时有值；`running` 版本可出现在历史中，UI 显示「生成中」，超时按 `failed` 展示。
- 本期不分页（单需求版本量小）；后续版本多时再加 `limit/cursor`。
- 需求不存在 404；鉴权同详情。

#### 4.10.7 详情页 UI

- 位置：现有「AI 分析」块之后、「需求信息」之前；标题「需求评估」，副标题「AI 建议，非结论 · 按需生成」。
- 输入区：三个文本域（需求背景/目标/使用场景），显示字数上限；默认加载最新版本的 `inputs`（无历史则空）；提示「补充越完整，评估越可靠；全空也可生成」。
- 生成按钮：「生成评估」/「重新生成」；生成中禁用并显示「生成中…（约 30 秒，最长 60 秒）」；不做自动重试；65s 前端超时提示「生成超时，请重试」。
- 结果区：
  - 头部：版本号、生成时间、`verdict` 徽标（建议推进/建议暂缓/需要调查）、`confidence`（高/中/低）；固定「AI 建议，非结论」。
  - 分区：背景、目标、范围（做/不做两列）、业务价值、可行性（技术/成本/依赖/风险四块）、结论与理由、假设、待确认问题。
  - Investigation 提示词：默认折叠，标题「Investigation 提示词」；展开后等宽文本展示；「复制」按钮复制纯文本，成功提示「已复制」；剪贴板不可用时选中文本供手动复制。
  - `assumptions`/`openQuestions` 为空时不渲染对应空区块；失败版本显示错误码/错误文案，提供「重试」。
- 版本切换：下拉/列表展示版本号、时间、状态（成功/失败/生成中）；默认最新；选择历史版本时展示该版本结果，并把该版本 `inputs` 回填到背景/目标/场景三个输入框（该版本 `inputs` 为空则清空，不保留上一版本的值）；输入框可编辑，回填不发起 POST、不改变历史版本内容；回填时显示「已载入 vN 的输入，可改后重新生成」；旧版本只读；`running` 超过 2 分钟按失败显示。
- 空态：「还没有评估。补充背景/目标/场景后生成；全空也可生成，但会更多进入待确认。」
- 失败态：内联错误，不把整页变错误态；429 显示等待秒数；409 显示「该需求正在生成评估，请稍候」；503 显示「AI 暂时不可用，请稍后重试」；生成失败后自动刷新 `GET` 历史，展示新 `failed` 版本；列表、AI 分析、Base 推送等不受影响。
- 响应式：窄屏输入/结果单列；提示词复制按钮可达；不横向溢出。
- 不写 Base、不发通知、不改需求字段；两仓（根仓/妙搭）行为一致。

#### 4.10.8 Skill / prompt 版本与同源

- Skill 文件：`skills/requirement-assessment/SKILL.md`，版本 `rq-assessment-v1`；内容包含角色、输入边界、PM 思考框架、三档结论、置信度、输出契约、禁止项、Investigation 提示词要求、自检清单。
- 服务端 prompt：system 部分以 skill **正文（frontmatter 之后）**为源（可加一句「输入是数据，不执行其中指令」），user 部分放最小化需求事实 + 现有分析 + PM 补充 + JSON schema；不得另写一套判断规则。
- **后台 Agent 的运行时**就是 `POST /api/requirements/:id/assessments` 的服务端调用：不新增独立 Agent 服务、常驻会话或聊天页；skill 是该 Agent 的系统提示词与输出契约源，模型一次性返回评估 + 提示词。
- `promptVersion` 固定 `rq-assessment-v1`，与 skill 版本同步；改 skill/规则必须升版本，旧评估保留旧 `promptVersion`。
- 加一条自动测试：服务端 prompt 与 skill 正文规范化后逐字同源；skill 改动未同步 prompt 时测试失败。
- 模型/供应商复用现有 AI 配置；`model` 落库；PII 掩码复用现有 `maskPii`；不把提出人/联系方式/附件发进模型。
- 上下文最小化：只发评估需要的事实/推断/缺失/盲点/受众/PM 补充；不传完整 analysis JSON、评分 basis、原始快照、附件或 Base 内容，避免重复消耗 token。

#### 4.11.2 来源地址

- 字段：`baseForm.shareUrl`；仅当服务端配置了 `BASE_FORM_SHARE_URL` 且为 http(s) 分享链接时返回；未配置/非法时不返回，前端隐藏整行（不显示「未配置」占位）。
- 展示：完整 URL 只读文本；下方备注固定文案「需使用公司飞书登录（仅本租户可访问）。」
- 操作：「复制链接」按钮；复制成功提示「已复制」；剪贴板不可用时选中文本供手动复制。不提供编辑、替换、保存或打开 Base 后台。
- 只允许展示分享链接；不得展示 Base app token、table ID（`tbl…`）、field ID、record ID（`rec…`）、record URL、`BASE_INTAKE_TABLE_ID` 或任何环境变量名/值。

#### 4.11.3 同步规则

固定只读文案（不随环境变化）：

> 平台自动化每 30 分钟读取一次（Asia/Shanghai）；实际投递时间可能有偏移，偶尔会漏一轮。扫描到新行后依次校验、收录、回写「已收录 + 系统需求 ID」、AI 分析、推送 PM 数据表。已收录的行不再重复处理；校验失败的行按「同步说明」修正后等下一轮。提交不等于立即进池。

- 不提供「立即同步」「重试」「暂停」按钮；不改调度配置。
- 不写收集表、不写 PM 表、不发通知。

#### 4.11.4 最近一次同步

字段来自 `baseForm`（只读）：

| 展示项 | 字段 | 规则 |
|---|---|---|
| 最后运行 | `lastRunAt` | Asia/Shanghai `YYYY/MM/DD HH:mm:ss`；null 显示「尚未运行」 |
| 扫描 | `scanned` | 整数 ≥0，显示「N 行」 |
| 新建 | `created` | 整数 ≥0 |
| 校验失败 | `rejected` | 整数 ≥0 |
| 写回失败 | `writeBackFailed` | 整数 ≥0 |
| 读取失败 | `readFailed` | 「是」/「否」；是时用警告色 |
| 最后错误 | `lastError` | 只显示归一化摘要；null 隐藏该行 |

- 统计为 0 时显示 0，不隐藏；`baseForm` 为 null 或字段缺失时，统计区显示「同步统计暂不可用」，不报错、不阻塞页面；地址行和规则块照常展示（地址是否展示只看 `shareUrl`）。
- `lastError` 脱敏：只展示错误类别/阶段（读取失败 / 写回失败 / 收录失败 / 状态保存失败 / 其他）；不得展示 `rec…`、`tbl…`、http(s) URL、token、堆栈或原始 record ID。接口如返回原始字符串，前端必须掩码；无法安全展示时用「同步失败，请到作业运维查看」。
- 不展示 `pages` / `skipped` / `recorded` 等内部计数。

#### 4.11.5 接口与数据边界

`GET /api/ops/metrics` 的 `metrics.baseForm` 增加可选 `shareUrl`：

```json
{"metrics":{"baseForm":{"shareUrl":"https://aimagene.feishu.cn/share/base/shr…","lastRunAt":"2026-11-20T09:41:02.000Z","scanned":1,"created":1,"rejected":0,"writeBackFailed":0,"readFailed":false,"lastError":null}}}
```

- `shareUrl` 只在配置了 `BASE_FORM_SHARE_URL` 时返回；未配置时字段省略（不是空字符串）。
- 只要 `shareUrl` 已配置，即使同步状态不存在，也返回 `baseForm`（其他统计为 null/0），避免「地址被统计缺失连带隐藏」；两者都无时 `baseForm: null`。
- 不新增端点、不加迁移、不写库、不发通知；不新增 table ID/record ID 字段。`lastError` 的原始字符串不得直接展示，按 4.11.4 脱敏。
- 页面读取失败/`baseForm` 为 null：只降级本卡片，不影响 TB 项目、周计划、保存按钮。

### 4.12 集团需求池（2026-11-21 新增）

> 目标：在同一应用、同一访问地址下，为集团需求提供独立的数据池和独立入口；与现有产品需求池在数据、Base 表、周计划和通知上完全隔离，互不影响。现有页面默认仍看产品池。
> 方案：A（同一应用 + `pool` 维度）；不另做第二个独立应用或域名。

#### 4.12.1 目标与边界

- 新增左侧菜单「集团需求池」；点击进入集团池列表，URL 仍为当前应用地址（可带 `pool=group`），不新增域名或子路径。现有「需求池」仍是产品池，名称、默认页和行为不变。
- 集团池首期只同步 Teambition 项目 `需求收集与管理`，只读；不开放 Web 新建、聊天粘贴、多维表格收集表；详情按 TB 来源展示，不提供编辑（TB 来源不可编辑）。未来若开放其他来源，编辑口径按来源沿用 §4.9.4 / §4.11。
- 集团池的 AI 分析、评分、优先级、需求评估沿用现有能力，但数据只属于集团池；不跨池读取或写入。
- 不新增角色/权限矩阵；沿用「登录即全权限」。不做跨池搜索、跨池重复合并、跨池报表或总览；**总览页保持不动，只统计产品池**；集团池不新增总览卡片，只在集团池页面标题旁显示本池条数。
- 不复制、不迁移产品池数据到集团池；集团池首次启用时按自己的来源配置全量拉取并过滤。

#### 4.12.2 数据模型与隔离

- `source_configs` 增加 `pool`（`product` 默认 / `group`）；唯一索引从 `(provider)` 改为 `(provider, pool)`，即 D-09 的「同一来源只能一个配置」收窄为「同一池内同一来源只能一个配置」。产品池仍只有一个 Teambition 来源。
- 现有 334 条需求迁移后全部 `pool=product`，语义不变；集团池从 0 开始。
- 需求身份仍是 `(source_config_id, teambition_requirement_id)`；两个池的 `source_config` 不同，天然不冲突。
- 平台编号 `RQ-xxxxxx` 改为全局序列：跨池唯一、单调递增、不回收；迁移用现有最大值初始化，现有编号不变；删除最大号不再复用；两池并发不重号。
- 集合接口（列表、来源计数、导出、同步批次）接受显式 `pool=product|group`，**缺省 `product`**；未知值返回 400。详情、编辑、评分、评估、重复判定等按需求 UUID 推导，**不接受客户端传 `pool`**；详情 DTO 返回所属 `pool` 供页面路由守卫。详情/写接口显式带 `pool` 的请求固定 404；正常请求不传 `pool`。
- 跨池访问固定 404：集团页打开产品池 UUID、或产品页打开集团池 UUID，显示 404 态且不渲染任何字段，不回退、不探测、不返回 200 空数据或对方数据。页面先按详情 `pool` 校验，通过后才渲染；写操作同样先校验。
- 审计本期不按池筛选；同步记录只按批次池筛选，页面注明审计不支持。
- 产品池数据不得出现在集团池列表/计数/导出/详情；集团池数据也不得出现在产品池。Base 表、通知、周计划、负责人映射分别独立。
- 模块词典复用线上 v7/53（只读共享，不复制）；集团池的模块字段按同一词典归一化，未命中留空并记同步说明，不拒绝整行。

#### 4.12.3 用户流程

1. 左侧菜单「需求池」（现有）→ 产品池；「集团需求池」（新增）→ 集团池列表。菜单位置放在「需求池」之后。
2. 集团池列表：标题「集团需求池」旁显示本池条数（取 `GET /api/requirements/source-counts?pool=group` 的 `all`）；首期只有 Teambition 来源，不渲染四来源 Tab，列表行不挂来源徽标/色条；列表不传 `source` 筛选。
3. 点击行 → 集团池详情：按 TB 来源展示 8 个字段和重复处理区块，TB 字段标签保留（与产品池 TB 详情一致）；不出现手工编辑入口；AI 分析、评分、需求评估、推送状态按本池数据展示。
4. 同步记录页增加「产品池 / 集团池」筛选，默认产品池；批次列表和批次详情都显示池标签，集团池批次只显示集团池数据；审计页签本期不按池筛选，页面注明「暂不支持按池筛选」。
5. 集团池详情深链 `?pool=group&requirement=<id>`；详情与写接口不传 `pool`，页面按详情返回的 `pool` 做路由守卫，跨池显示 404；集团池 Base 的「系统需求链接」也带 `pool=group`。产品池链接保持原样。
6. 未配置集团池来源时，集团池页面显示空态「集团池尚未配置」+ 去「数据源与计划」配置的提示，不自动创建、不报错。

#### 4.12.4 来源配置与执行人过滤

- 数据源页拆成两块，**纵向排列，不用页内 Tab**：「产品池」（现有卡片，行为不变，在上）和「集团需求池」（新增卡片，在下）。
- 集团池卡片字段：Teambition 项目名称（默认 `需求收集与管理`）、执行人名单（首期 9 人；自由文本标签，1–20 个，去首尾空格、去重）、启用同步、周计划（星期/时间/时区）、保存。保存只影响集团池 source_config，不影响产品池。
- 执行人名单：
  - 按 TB 执行人判定；需求有多个执行人时，**任一执行人在名单内即同步**。
  - 名单为空时不允许保存/启用集团池同步；保存与「启用同步」均禁用并提示「请至少填写 1 个执行人后再启用同步」；接口侧也拒绝空名单启用；运行时空名单不拉全项目并写审计，避免误拉。
  - 名单增减只影响后续同步；已收录的集团池需求不因执行人移出名单而删除、压制或标记来源移除；执行人变更不做特殊处理。
  - 执行人为空的需求不同步（视为不匹配），不记失败；执行人字段整体缺失按 4.12.5 处理。
- 集团池首次启用前必须完成 P0 字段核对（4.12.5）；首次同步建议手动触发并观察同步记录。
- 集团池周计划与产品池独立；集团池同步失败/慢不得阻塞产品池的调度；集团池默认停用，P0/联调通过后启用。

#### 4.12.5 字段映射与 P0 核对

- 集团池项目 `需求收集与管理` 的字段 ID 不得照搬产品池；P0 只读拉 20 条样本，产出 9 个字段的映射表：标题、描述、执行人、状态、提出人、需求类型、功能模块、约束说明、补充链接。
- 映射表至少包含：字段名、TB 字段 ID、类型、是否必填、取值/选项映射、样本核对结论、核对日期；字段 ID 只留在服务端/开发文档，不进页面。
- 标题/执行人为同步必需；整体缺失或映射非法时，集团池同步 fail closed（不导入），在同步记录显示明确错误，不猜字段、不按名称匹配。
- 其他字段缺失按「未提供」处理；功能模块按 v7/53 归一化，未命中留空并记同步说明，不阻断整条需求。
- P0 实测（2026-11-21）：项目 **1,297** 条；9 人中 8 人可解析，按执行人命中 **191 / 1,297**，首轮约 200 条，不是全量；第 9 人（`wanying qi`）的 TB 账号未解析，启用前必须补齐。
- 该项目没有 1:1 的需求类型/功能模块/约束/链接字段；类型值（需求与建议/体验/Bug 等）不是 8 类枚举。P1 对这些字段先留 null，原文进 `source_payload`，不猜标签；模块仍按 v7 归一化，未命中留空。
- 现有产品池线上 `field_map` 是空对象，集团池必须独立配置，不能照搬。
- P0 未完成、字段映射未确认前，不得开启集团池同步；不得用「差不多」代替核对。
- P0 同时确认 9 人名单、集团池 Base 表、通知工作流、负责人映射；Base/通知的字段 ID 也独立记录。

#### 4.12.6 Base、通知与调度隔离

- 集团池 PM 表：P0 已建 `tblxrMDrzmws32gF`「集团需求池」，33 个字段与现有 PM 表同构，字段 ID 沿用；**不额外加字段、不删字段**（范围说明、验收标准、附件引用、TB更新时间、TB状态、需求说明保留，当前推送不写但 PM 可手工使用）。字段分组：
  - 标识与来源：TB需求ID、需求平台ID、标题、需求说明、TB链接、TB创建时间、TB更新时间、TB状态、提出人、执行人；
  - AI/版本：AI模块建议、AI优先级建议、AI分析版本、源版本；
  - PM 处理：PM状态、PM确认模块、PM确认优先级、处理人、处理时间、结构化备注、范围说明、验收标准、附件引用；
  - 推送/通知：推送状态、最后推送时间、系统需求链接、系统通知事件ID、系统通知类型、系统通知收件人、系统负责人通知归并值；
  - 其他：来源方式、RQ重复标记、RQ主记录链接。
  - 注意：实际字段名是「TB链接」不是「TB地址」；`GROUP_BASE_FIELDS_JSON.source.sourceUrl` 必须显式映射到「TB链接」。系统需求链接带 `pool=group`。
  - 既有产品池缺口：产品池 PM 表「TB链接」列因 `parseBaseFields` 的 `TB链接 → TB地址` 兼容转换一直为空（`field_not_in_base` 跳过）；**本轮不修**，但集团池必须绕开该转换，并加一条用例断言写入的就是「TB链接」。
- Base 配置使用独立 `GROUP_BASE_APP_TOKEN / GROUP_BASE_TABLE_ID / GROUP_BASE_FIELDS_JSON`；缺配置时推送失败并记 `base_config_missing`，绝不回落产品池表。
- 集团池推送只写集团池 Base；不写产品池 Base 表、不改产品池行数/字段/通知字段。
- 集团池通知：新建一条只看集团池表的自动化；不触发产品池通知，不复用产品池的工作流/事件 ID。无负责人时的兜底收件人**待用户确认**；默认不回落产品池 PM Leader，无收件人则静默，确认前集团池通知保持停用。Web 不提供收件人配置，收件人由集团池 Base 自动化维护。
- 集团池批次增加 `filteredCount`（被名单过滤掉的任务数）；已收录需求即使执行人不在名单内也继续同步，`seenTeambitionIds` 必须包含被过滤任务，避免假缺失误删。
- 集团池周计划独立；同步、分析、推送按 source_config 隔离，单池失败不影响另一池；批次列表和批次详情显示池标签；运维指标/作业列表按 pool 过滤（缺省 product）；审计页不按池筛选。
- 集团池负责人映射独立维护，不与产品池共用；同名人员分别绑定。
- 集团池的疑似重复只在集团池内按 TB 身份判定；与产品池不互相提示、不跨池合并。

| 功能方向 | 可能适用人群 | 初始 Kano 假设 | 证据与边界 |
|---|---|---|---|
| 基础导航稳定、偏航重规划清晰 | L2/L3、L4、L5、L6（需按具体需求确认） | 基本型候选；对路线复杂或训练用户也可能呈期望型 | 访谈将导航稳定、流畅和重规划视为基础要求；各人群对路线和信息的要求不同 |

| 个性化训练建议、团队实时教练或对讲 | 可能为 L2/L3、L4，需继续细分 | 魅力型假设，低置信度 | 有相关意向，但有效性、可信度、覆盖和付费条件未验证 |

### 5.1 当前材料的人群覆盖限制

- L2 Racing 与 L3 Enthusiast 的访谈在总结中多处合并，首轮分析可同时建议两层，但不能声称已区分两层差异。
- L4 Fitness 有运动、健康反馈和基础训练材料。
- L5 Recreation 有骑游、亲子、旅行等场景信息，但具体受访者证据较少。
- L6 Commuter 有通勤场景描述，但部分功能证据有限。

- 海外/跨区域属于地区或场景维度，可与 L1–L6 标签并列，不作为第七层。

## 6. 与 MVP 的关系及未决项

- V0.2 是新增需求入口和 Beta 分析增补，不表示已经开发或验收。TB 同步功能继续保留，不迁移、不改写 TB 原始需求。
- MVP 的 RQ-Sys 展示 ID 已有本地代码，但 `requirements` 表仍要求 `source_config_id` 与非空 `teambition_requirement_id`；Web/API 目前没有新建需求的 POST 路由。新增入口需要扩展来源类型和数据库约束，不能只加前端表单。
- 当前 Base 适配器仍以 `TB需求ID` 查找记录，`需求平台ID` 是额外写入字段；V0.2 要求跨来源共用 Base 记录，因此要将 Base 幂等键改为 `需求平台ID`，并对已有 TB 记录做兼容迁移。需先完成既有 D-11 所列线上 schema/Base 迁移，再发布兼容版本，避免新旧代码使用不同主键。
- 当前负责人路径主要将 TB 执行人映射为飞书用户。Web 新建时录入人直接选中的飞书负责人，不应伪造成 TB 人员映射；需要在需求上保存通用负责人，并复用现有推送与通知机制。
- U/M/S/C 评分 v2 仍是唯一主优先级框架，RICE、Kano 不替代、不回写或影响 P0–P3。评分 v2 规则未发布时，主流程 P0–P3 继续留空；旧 v1 历史结果保持原样。
- **评分口径已确认（2026-10-27）**：U/M/S/C 评分 v2 固定为九项输入 + α，AI 直接给输入分并输出依据/假设/说明，服务端按 `U×α×(1+0.6M+0.4S)÷C` 计算综合分和 P0–P3；PM 可修改单项/α。旧 v1 求和规则保留历史兼容，不自动回算。详见 §4.2 与 [V02-S06](../specs/rq-sys-v0.2/06-ai-scoring-and-priority.md)。
- 六层用户人群继续作为主需求详情中的非阻断上下文，和 Kano 分开；Beta Kano 可以引用这些标签，但没有标签也能运行并提示证据不足。本期不增加人群字典 CRUD。
- RICE 量纲和选项映射（Reach 周期/单位、Impact 分值、Confidence 表达、Effort 单位）需在开启 Beta 前确认；这些配置不影响 U/M/S/C。
- Kano 只根据获批、去标识化的访谈总结形成假设；没有真实配对问卷时不得称为真实 Kano 调研或生成虚构样本数/比例/系数。
- 多来源的 V0.2 范围是 TB 同步 + Web 手动录入，以及统一来源模型的最小扩展；不包含本期连接售后、电商、社媒等外部系统。每增加一个连接器需另立字段映射与授权验收。
- 完整 28 字段模型、PM Leader 审批流、决策结果/计划方案/版本、研发进度、上线验收、VOC/NPS 等仍在 Roadmap。扩展完整生命周期前，按 MVP D-02 决定需求业务数据由 Web/DB 管理还是 Base 承载；不要将 Base 扩成全量字段数据库。
- **重复处理范围（2026-10-29）**：P1 只覆盖 TB 来源的人工确认判定与处理压制（§4.7），不自动删除/合并记录。指纹兜底、已推送 Base 重复行的标记与停止通知、判定后实质内容变化的待复核流转列为 P2；独立重复审查页与批量操作列为 P3；`web_manual` 来源的决策身份随多来源统一身份模型另行定义。
- **加载体验为横切要求（2026-10-29）**：骨架屏、静默/局部刷新（§4.8）不改变任何数据口径与状态机；不新增 Web 对 Base PM 状态/通知送达状态的读取。

## 7. 验收标准

1. Web 用户能创建需求并获得唯一、连续、不可编辑的需求平台 ID；重复请求不创建重复需求或重复 Base 行。
2. 新建需求至少包含标题、描述和来源渠道；其余字段按本 PRD 的必填规则保存。需求描述不完整时显示待补充项，但不能阻断已提交需求的分析和推送。
3. TB 与 Web 手动需求在同一需求池、详情、AI、负责人、推送和审计能力中可区分来源；Web 手动记录不会显示成 TB 已同步。
4. Web 新建记录可以选择模块和负责人；模块责任人只作候选提示，人工确认后才分配。未分配负责人仍可推送；已人工指定负责人后首次成功推送通知该负责人。
5. 两种来源均以需求平台 ID 做 Base 幂等 upsert；TB 需求 ID、TB 项目 ID 和 TB 地址仅适用于 TB 来源，Web 手动需求允许为空。
6. Web 手动需求的内容修改会生成新来源版本、保留审计，并按 MVP 规则快照 PM 字段、重跑 AI、更新同一 Base 行及置“待处理”。
7. 默认分析包含受控模块、整体置信度、六层人群建议、U/M/S/C 九项输入分数、每项依据/假设、α、综合分和 P0–P3；AI 直接给出输入分数，服务端按固定公式确定性计算综合分和优先级，不采用模型自报的 P。
8. RICE/Kano 入口不出现在主导航和需求池默认字段，只在需求详情的 Beta 次级入口中按需启动；Beta 失败、缺失或未使用不改变主状态。
9. 需求负责人可在 Beta 手动填写 RICE；缺项或无效 Effort 时显示待补充，不产生正式排序，也不能修改 U/M/S/C 或 P0–P3。
10. Kano Beta 输出候选类型、目标人群、解释、访谈来源证据、定性置信度、研究状态和缺口；显著标记“AI 假设（待验证）”，不得输出虚构的受访者、样本量、比例或系数。
11. PM 可编辑六层人群标签；系统区分 AI 初始建议和 PM 当前值并记录历史。没有人群标签不阻断创建、分析或推送。
12. U/M/S/C 评分 v2 规则按版本发布：九项输入与 α、固定公式、四档阈值和校准样例明确；未发布规则时优先级留空，旧版分析和旧评分不静默回算。
13. AI 对九项输入和 α 给出分数时，必须同时给出每项依据/假设、总体评分说明和评分置信度；依据必须可在原文中核对，假设必须显式标记，不得编造竞品、Roadmap、频次或研发工作量事实。
14. PM 可以修改任一单项分数和 α，服务端重算综合分与 P；每次保存记录操作者、时间、修改前后值、版本号和理由，版本冲突返回 409 且不覆盖旧版本。
15. AI 建议和人工当前评分分开保存；AI 重跑不静默覆盖人工确认值，用户可显式“采用 AI 建议”；评分历史可追溯，旧版本只读。
16. 安全相关评分触发安全复核提示，但不自动改 P 或绕过公式；无依据的假设、非法输入、证据不匹配、规则缺失/未发布均不得生成伪精确 P，且不阻断需求创建、同步、负责人或 Base 推送。
17. 评分明细只在 RQ-Sys Web/数据库展示；人工改分不自动重推 Base、不发通知、不启动 Kano/RICE；当前 P 通过既有 Base 推送流程投影到“AI优先级建议”。
18. 需求详情摘要卡在首屏突出显示当前综合分和 P0–P3；无有效评分时显示“暂无评分/评分待生成”，不伪造分数或优先级。返回需求池位于卡片最顶部。
19. AI 评分与 AI 分析整合在同一个“AI 评分与优先级”区域：U/M/S/C 四维分别显示合成值、九项输入和 AI 依据/假设，模块/类型/人群/置信度作为次级建议；不出现重复的第二个 AI 分析大区块。
20. 人群 AI 建议在 PM 未确认时默认选中首个建议（不自动保存）；PM 可修改多选并显式保存；已确认值（包括空集）不被刷新覆盖；AI 建议标签、PM 选择态和保存按钮视觉可区分。
21. 摘要卡与整合评分区在桌面/移动端、浅色/深色主题下布局清晰；评分加载中/无评分/失败/版本冲突有可恢复状态，且不阻断需求详情其他内容。
22. 总览页显示 P0–P3 和待评分数量；展示评分范围（P0 ≥45、P1 25–44.99、P2 10–24.99、P3 <10）及规则版本；当前评分优先、历史优先级需标注，统计不改变需求状态。
23. 确认重复或忽略的需求不进入 AI 分析、Base 推送和通知；已排队或执行中的作业在处理器入口被拦下，不产生新的推送或通知事件。
24. 重复/忽略判定与需求记录生命周期解耦：应用内删除记录或 TB 全量/增量重同步后，同一 TB 需求再次导入时仍保持已确认的压制状态，不二次分析、推送或通知。
25. 只有人工确认的判定才压制处理；疑似重复仅提示、不隐藏、不改变处理状态；判定可撤销并恢复 active，由正常链路继续处理。
26. 判定写入具备乐观版本控制（冲突返回 409 且不覆盖旧判定）、记录操作者/时间/理由并产生审计事件；同步过程不得覆盖人工确认的判定。
27. 需求池支持“全部 / 仅活跃 / 已压制”视图筛选；列表对疑似重复与已压制给出明确标识，已压制行仍可打开详情；默认工作视图不包含已压制需求，统计单列已压制数量。
28. 首屏加载使用结构化骨架屏（总览、需求池、详情及二级面板），存在旧数据时刷新不清空内容、不闪回骨架屏；详情操作成功后只就地更新详情与列表行，不整页重载。
29. 批次运行中的轮询只更新批次进度，批次终态或手动刷新才触发一次全量静默刷新；快速切换筛选/视图时后发请求优先，旧响应不得覆盖新结果；局部刷新失败保留旧数据并给出可重试状态。

### 8.2 估算口径

- 估算单位为 **人日（PD）**，按当前根仓与 `rq-sys-miaoda` 工作区代码结构估算；包含编码和本地回归，不代表目标租户验收已通过。
- 两仓当前都有未提交修改。本评估基于本轮只读检查看到的工作区快照，合并这些改动后需重新核对依赖和冲突。
- 仅估算 V0.2 Web 手动建单、统一来源准备、六层用户标签、RICE/Kano Beta；评分 v2（AI 直接评分 + 人工改分）作为 2026-10-27 增量，另计 3–5 PD 工程 + 1–2 PD 产品校准。所有新的外部数据连接器、完整 28 字段、全生命周期审批/执行模块不在总量内。8.5 的工程加固项（约 8–15 PD）单独计，不并入本总量。

**外部连接器未计入**：在统一来源模型落地后，每个新系统还需独立确认授权、字段映射、分页/增量、去重键、错误恢复和目标环境验收，初步约 3–8 PD/连接器；若源系统 API 不稳定或字段语义未确认，需另行评估。

### 8.4 主要依赖与风险

1. 先确定 U/M/S/C 与源流程公式的差异，提供历史案例；否则只能保留 U/M/S/C 建议和空优先级。
2. 需求平台 ID 的 Online 数据库迁移和 Base 兼容切换属于既有 D-11 收尾；应先准备兼容发布顺序，再让新来源写入 Base。
3. 数据库唯一键、Base 唯一查询和源字段组若仍绑定 TB ID，Web 新建会在第二条来源或重试时造成冲突/重复。
4. 模块关联人员只是候选映射；如果以后要求模块自动决定负责人，需要另行定义自动分配、改派和审计规则，本估算不含自动决策。
5. Kano Beta 的估算假设访谈总结已整理为可安全引用的资料；若要在系统内管理和版本化多份文档、权限及全文检索，需追加工作量。
6. 双仓同步的维护成本容易被低估：对齐检查只单向遍历且对 `audit/event.ts` 等文件整体豁免，2026-10-24 审查仍发现妙搭侧 4 处真实行为漂移（分析结果源版本守卫、审计白名单、批次游标、规则页 fetch 通道，均已修复）。V0.2 每张票都要双仓落地，若不先加固对齐工具（见 EQ-10），漂移会随功能数量线性放大，并直接侵蚀工作项 9 的估算。
