## 2. 系统现状（确认前后的行为边界）

- 规则版本机已就绪：草稿 → 发布（原子退休旧版）→ 新分析/人工重跑确定性计算 P0–P3；未发布时 priority 一律为 null（Base 不写该字段）。
- Base `AI优先级建议` 单选已含 P0–P3（正式表与 POC 表均已核对）。
- 规则发布后**不自动回算**历史需求；仅影响之后的分析与"重新分析"。
- 规则 JSON 不符合契约时 `buildPriorityRule` 返回 null——错误规则不会上线产出伪优先级。

## 3. 需要提供的输入清单

1. 公式定稿（上表 #1/#2/#4 的选择，最好附一个手工算例）。
2. 每维取值→分数映射表（U/M/S/C 各一张；建议 3–5 档）。
3. P0–P3 阈值（若选综合分阈值；给 3 个切点）。
4. 历史校准案例 ≥10 条：`{标题摘要, U/M/S/C 取值, 期望 P 值}`；发布时逐行粘贴（现有 JSON 校验要求每行一个对象）。
5. 确认人（PM Leader）与发布窗口。

## 4. 确认后的实施口径（已按 V02-T10 排期，2–4 PD）

- 若选 B 公式：调整 `priority-rule.ts` 计算器与 schema（阈值不再是 0–4 的求和上限），规则管理 UI 复用。
- 校准证据校验保持现状：发布必须带非空校准记录。
- 发布动作走现有"草稿→发布"流，无需停机。
