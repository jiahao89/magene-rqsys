## 1. 背景与问题

系统已跑通「定时同步 → AI 分析 → 负责人映射 → Base 推送 → 通知」主链路，并完成 321 条真实需求重跑与评分采纳。但要作为 PM 团队的日常系统投入使用，仍有以下阻塞：

1. **协作面不在真实环境**：线上 Base 仍指向测试 Base「TB同步测试(可删除)」，正式「TB需求池」未授权应用；278 条已推送记录落在测试表，真实 PM 看不到、收不到通知。
2. **优先级没有区分度**：当前 P0=0 / P1=0 / P2=7 / P3=314；AI 实际只看到标题，M/S 证据缺失导致 M=S=1 占 93.7%，α 归一后 P0/P1 不可达；阈值/α/直通规则未定稿；人工优先级只存在应用内、不回写 Base；需求池无法按优先级分诊。
3. **运营与治理缺口**：负责人无匹配（43 条）停推且不可批量处理；无 AI 质量校准与采纳率；PM 决策闭环未定义（Base vs Web）；无角色权限；无日报/周报与运营指标；AI 配额曾耗尽且无告警；备份/恢复/环境隔离未验证；无角色化培训 SOP。

## 2. 目标与非目标

**目标（试点上线 4 周内）**
- 真实 PM 在正式 Base 看到需求、收到通知，且 Base 与应用数据一致可回读。
- 优先级结果可解释、可区分，PM 的人工判断能进入协作面并驱动排期。
- 建立最小运营闭环：角色权限、负责人维护、AI 质量与运营指标、可靠性告警、备份恢复、培训 SOP。

**非目标（本期不做）**
- 完整 28 字段需求模型、全生命周期（规划/研发/上线/VOC）闭环。
- 多来源连接器（售后/销售/电商）、TB 增量与删除检测。
- 移动端投入（维持 PC-only）、复杂评论/评审协作。

## 5. P0 需求

### R-P0-1 正式 Base 与通知闭环

**用户故事**：作为 PM，我希望在正式「TB需求池」中收到/处理需求，并收到飞书通知，而不是在测试表里自转。

**验收标准**
1. 线上 `BASE_APP_TOKEN/BASE_TABLE_ID` 回读确认指向正式 Base/表；正式表已授权应用可编辑。
2. 字段/选项/`BASE_FIELDS_JSON` 对齐校验通过（含 `AI优先级建议` 选项扩展策略）。
3. 用 1 条真实需求完成：首推写正式表 → 回读平台键/负责人/PM 状态/AI 字段 → `owner_assigned` 通知实收 → 实质变更 `substantive_update` 再次实收。
4. 应用启动时校验 Base 身份与预期环境一致（指纹 env），不匹配 fail-fast。
5. 回退演练：10 分钟内可切回测试 Base/关闭通知，且不丢应用数据。
6. 279 条已推送记录与正式表行数对账（或明确不迁移、重建口径）。

### R-P0-2 优先级可用性与分诊

> **2026-11-06 决策（PRD-14）**：AI 优先级改为**相对分位**（活跃池内校正总分排名：P0≈前 5%、P1≈下 15%、P2≈下 30%、其余 P3；安全标记强制 P0）；PM 终审优先级在 Base 维护；Web 不进 Base 写回。

**用户故事**：作为 PM，我希望看到有区分度的优先级，并能按优先级筛选/排序，而不是 98% 全是 P3。

**验收标准**
1. **口径定稿**：解决两套阈值冲突，发布 v3 规则（含 α 口径、直通规则、安全升 P）；明确 AI 建议与 PM 终审的关系。
2. **业务上下文**：至少接入 Roadmap/战略主题/硬依赖等全局上下文与 TB 描述/验收字段映射；单需求补充上下文保留并可重跑。
3. **人工优先级口径**：PM 终审优先级在 Base 维护（PRD-15/18）；Web 人工覆盖仅用于应用内排序/预览，不写 Base、不触发通知。
4. **分诊视图**：需求池列表显示优先级，支持 P0–P3 筛选、按优先级排序、模块/人群筛选（≥1 个维度）、总览分级卡下钻（批量确认随 PR-04 取消，见 PRD-18）。
5. **校准验收**：以 PM Leader 人工排序的 20–30 条真实需求为基准，P0+P1 占比可解释（参考 ≥10%）且 Top20 重合率 ≥70%；若产品决定「仅参考」，须同步修订 PRD/验收标准并停止以分级作为卖点。

## 8. 数据迁移与切换计划

1. **只读盘点**：回读线上 env、正式 Base 行数、测试 Base 已推送 279 行、字段选项差异。
2. **决策**：正式表沿用「TB需求池」还是新建；已推送 279 条是否回填正式表（按 TB ID + 平台键对账）。
3. **切换窗口**：停定时同步与恢复触发器 → 切换 env → 发布 → 单条真实需求全链路验证 → 恢复触发器。
4. **回退**：保留测试 Base 只读；回退 env + 发布 ≤10 分钟；期间不接收新需求写入。
5. **清理**：确认正式 Base 对账后，测试 Base 标记只读并保留 30 天。

## 10. 运营指标（首期基线）

同步成功率与迟到时长、分析成功率/耗时/失败码分布、负责人自动匹配率与待匹配数、推送成功率、重复记录数、通知触发与送达、低置信度占比、AI 建议采纳/修改/暂不处理率、优先级分布与变化、需求积压与处理周期。

## 11. 风险与依赖

- 正式 Base 授权与字段调整依赖管理员/Base owner。
- 优先级口径依赖 PM Leader 人工基准与用户决策。
- AI 配额与供应商合规依赖采购/安全评审。
- 数据迁移旧记录依赖 TB 平台键稳定性（D-03 已确认 id 可用）。
- 文档/验收状态存在历史漂移，本增补启用后以当前状态页为准。

## 12. 发布计划（建议）

1. 第 1 周：Base 切换方案评审 + 优先级口径定稿。
2. 第 2–3 周：P0-2 实现与校准、43 条负责人清理。
3. 第 4 周：P1 最小闭环（权限、digest、指标、告警）、备份演练、培训。
4. 试点 2–4 周后复盘，满足 §9 后正式上线。
