## 2. 来源 A：聊天一键复制

**理解**：用户把聊天里的需求文字复制后粘贴到系统，AI 分析并自动填好必要字段，用户确认后创建。飞书聊天内容无法由系统直接读取，所以第一期用「粘贴框」，不依赖机器人权限。

**流程**
1. 需求池「新建需求」旁增加「从聊天粘贴」，弹出文本框（上限 20,000 字，与现有描述上限一致）。
2. 点击「分析」，服务端调用 AI 抽取字段，返回**草稿**，不落库。
3. 草稿填入现有新建表单，AI 填充的字段带「AI 填充」标记，用户修改后提交。
4. 提交走现有 `POST /api/requirements`，创建结果与手工收录完全一致。

**抽取字段**：标题（≤200 字）、整理后的描述、来源渠道（6 选 1，无把握留空）、需求类型（8 选 1）、产品型号、约束说明、功能模块（只能选已发布词典里的名称）、聊天中提到的提出人。

**设计要点**
- 草稿不入库：AI 不直接创建需求，必须有人确认。
- 聊天内容按不可信数据处理：模型输出必须通过 schema 校验，枚举值不在范围内就丢弃该字段，只填表单，不触发任何其它动作。
- 发给 AI 之前沿用现有 PII 脱敏；原始聊天文本默认不保存，只保存用户确认后的描述（见 §5 第 4 项）。
- AI 额度暂停（`readAiPause`）期间，该接口返回明确提示，用户可手工填写，不影响收录。
- 每个用户限流；审计只记录「发起了一次抽取」和字符数，不记录内容。
- 相似需求提示：草稿阶段用现有标题搜索（已有 pg_trgm 索引）列出最多 5 条相似需求，减少重复收录。

## 3. 来源 B：多维表格同步

**理解**：新建一张「需求收集表」，字段复用系统的收录字段。需求方在表里填写，系统定时读取新行并自动创建需求，同时把结果写回该行，让填写人看到反馈。

**收集表字段（与 `RequirementIntakeSchema` 对齐）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 标题 | 文本 | 是 | ≤200 字 |
| 描述 | 多行文本 | 是 | ≤20,000 字 |
| 来源渠道 | 单选（6 项） | 是 | 选项与 `REQUIREMENT_INTAKE_CHANNELS` 一致 |
| 需求类型 | 单选（8 项） | 否 | 与 `REQUIREMENT_INTAKE_TYPES` 一致 |
| 产品型号、约束说明、补充链接 | 文本 | 否 | 链接须为 http(s) |
| 功能模块 | 单选 | 否 | 选项取自已发布词典 |
| 提出人 | 人员 | 否 | 见 §5 第 3 项 |
| 系统需求ID、同步状态、同步说明 | 系统写回，只读 | | 状态：已收录 / 校验失败；失败时写明原因 |

**流程**
1. 调度 tick 读取收集表中「同步状态」为空的行（需要新增 Base 分页读取能力，见 §1）。
2. 逐行用现有收录校验：必填项缺失、枚举值不合法、链接格式不对，就不创建，只写回「校验失败 + 原因」。
3. 校验通过则创建需求，来源标记为多维表格；写回「系统需求ID」和「已收录」。
4. 之后走既有的 分析 → 负责人 → 推送，进入 PM 使用的「TB需求池」。

**设计要点**
- **收集表与 PM 的「TB需求池」必须是两张表。** 系统会往 PM 表写数据；如果收集表就是 PM 表，系统会把自己推送的行再次读成新需求，形成循环。
- **幂等**：以 Base 的 `record_id` 作为来源身份，同一行重复读取只创建一次；写回失败时下一轮按 `record_id` 补写，不会重复建需求。
- **只收录一次**：一期不同步收集表里的后续修改（见 §5 第 2 项）。行被删除不影响已创建的需求，与 Q4 一致，最多提示。
- **负责人不在收集表填**：沿用现有负责人映射与 Q1 口径，避免第二套指派入口。
- **失败可见**：读取失败、写回失败计入运维页和告警，沿用现有作业机制。
- **身份约束**：数据库现有约束要求 TB 行带来源配置和 TB ID、手工行两者为空（`0009`）。多维表格行需要新的来源类型（暂定 `base_form`）和外部 ID 列，需要一个新迁移，并同步妙搭侧。
