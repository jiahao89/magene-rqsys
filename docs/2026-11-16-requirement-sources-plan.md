## 2. 来源 A：聊天一键复制

**理解**：用户把聊天里的需求文字复制后粘贴到系统，AI 分析并自动填好必要字段，用户确认后创建。飞书聊天内容无法由系统直接读取，所以第一期用「粘贴框」，不依赖机器人权限。

**流程**
1. 需求池「新建需求」旁增加「从聊天粘贴」，弹出文本框（上限 20,000 字，与现有描述上限一致）。
2. 点击「分析」，服务端调用 AI 抽取字段，返回**草稿**，不落库。
3. 草稿填入现有新建表单（默认只填空白字段；覆盖已有内容前需确认），AI 填充的字段带「AI 填充」标记；用户修改某字段后撤销该字段标记，确认后提交。
4. 提交仍走现有 `POST /api/requirements`，校验与创建流程与手工收录一致；但请求额外携带 `intakeOrigin: "chat_paste"` 和可选的 `proposerName`。落库的 `source_type` 仍是 `web_manual`（本期不加新来源类型、不加迁移），来源区别记录在 `source_payload.intakeOrigin`，供 5c 的来源徽标/筛选与 Base「来源方式」使用（见 §5 第 6 项）。

**抽取字段**：标题（≤200 字）、整理后的描述、来源渠道（6 选 1，无把握留空）、需求类型（8 选 1）、产品型号、约束说明、功能模块（只能选已发布词典里的名称）、聊天中提到的提出人。

**设计要点**
- 草稿不入库：AI 不直接创建需求，必须有人确认。
- 聊天内容按不可信数据处理：模型输出必须通过 schema 校验，枚举值不在范围内就丢弃该字段，只填表单，不触发任何其它动作。
- 模型输出不可用时可以退化为「首行为标题 + 掩码原文为描述」，但响应必须带 `fallback: true`，界面明示「未经 AI 整理」，审计同时记录兜底状态与 `aiFilledCount`，不得把兜底计作一次成功的 AI 抽取。
- 发给 AI 之前沿用现有 PII 脱敏；原始聊天文本默认不保存，只保存用户确认后的描述（见 §5 第 4 项）。
- AI 额度暂停（`readAiPause`）期间，该接口返回明确提示，用户可手工填写，不影响收录。
- 每个用户限流；审计只记录「发起了一次抽取」和字符数，不记录内容。
- 相似需求提示：草稿阶段用现有标题搜索（已有 pg_trgm 索引）列出最多 5 条相似需求，减少重复收录。

## 3. 来源 B：多维表格同步

**理解**：新建一张「需求收集表」，字段复用系统的收录字段。需求方在表里填写，系统定时读取新行并自动创建需求，同时把结果写回该行，让填写人看到反馈。

**收集表字段（与 `RequirementIntakeSchema` 对齐）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 标题 | 文本 | 是 | ≤200 字 |
| 描述 | 多行文本 | 是 | ≤20,000 字 |
| 来源渠道 | 单选（6 项） | 是 | 选项与 `REQUIREMENT_INTAKE_CHANNELS` 一致 |
| 需求类型 | 单选（8 项） | 否 | 与 `REQUIREMENT_INTAKE_TYPES` 一致 |
| 产品型号、约束说明、补充链接 | 文本 | 否 | 链接须为 http(s) |
| 功能模块 | 单选 | 否 | 选项取自已发布词典 |
| 提出人 | 人员 | 否 | 见 §5 第 3 项 |
| 系统需求ID、同步状态、同步说明 | 系统写回，只读 | | 状态：已收录 / 校验失败；失败时写明原因 |

**流程**
1. 调度 tick 读取收集表中「同步状态」为空的行（需要新增 Base 分页读取能力，见 §1）。
2. 逐行用现有收录校验：必填项缺失、枚举值不合法、链接格式不对，就不创建，只写回「校验失败 + 原因」。
3. 校验通过则创建需求，来源标记为多维表格；写回「系统需求ID」和「已收录」。
4. 之后走既有的 分析 → 负责人 → 推送，进入 PM 使用的「TB需求池」。

**设计要点**
- **收集表与 PM 的「TB需求池」必须是两张表。** 系统会往 PM 表写数据；如果收集表就是 PM 表，系统会把自己推送的行再次读成新需求，形成循环。
- **幂等**：以 Base 的 `record_id` 作为来源身份，同一行重复读取只创建一次；写回失败时下一轮按 `record_id` 补写，不会重复建需求。
- **只收录一次**：一期不同步收集表里的后续修改（见 §5 第 2 项）。行被删除不影响已创建的需求，与 Q4 一致，最多提示。
- **负责人不在收集表填**：沿用现有负责人映射与 Q1 口径，避免第二套指派入口。
- **失败可见**：读取失败、写回失败计入运维页和告警，沿用现有作业机制。
- **身份约束**：数据库现有约束要求 TB 行带来源配置和 TB ID、手工行两者为空（`0009`）。多维表格行需要新的来源类型（暂定 `base_form`）和外部 ID 列，需要一个新迁移，并同步妙搭侧。

### 7.1 5a.1 口径补齐（2026-11-18 已发布）

以下修正已随 5a.1 实施并发布（release `7709402891559914800`，commit `9aaef82`）；目标环境结果见 §7.2 与 `.scratch/prd26-5a/RESULTS-20261118.md`。其中第 5 项的 `Retry-After` 展示在妙搭端未生效（E1），根因与修复见 §7.2。

1. **兜底标记**：`POST /api/requirements/intake-draft` 响应新增 `fallback`（布尔）与 `aiFilledCount`。模型输出不可用、标题/描述取自掩码原文时 `fallback: true`；界面必须明示「未经 AI 整理」；`intake.draft_*` 审计同时记 `fallback` 与 `aiFilledCount`，兜底不得计作一次成功的 AI 抽取。
2. **错误码分层**：供应商 `rate_limited` → 429 + `Retry-After`；`auth_error` / `request_error` → 500 并落一条服务端日志（不打印密钥与正文）；`timeout` / `network_error` / `analysis_failure` → 503。兜底成功仍返回 200，但必须带 `fallback: true`。
3. **来源留痕**：创建请求新增可选 `intakeOrigin: "chat_paste"`，写入 `source_payload.intakeOrigin`；`source_type` 仍为 `web_manual`，**不加迁移、不加新来源类型**。`intake.created` 审计带 `intakeOrigin`；5c 用该字段做需求池徽标/筛选与 Base「来源方式」。
4. **提出人落库**：创建请求新增可选 `proposerName`（≤100），写入 `requirements.proposer_name` 与 `source_payload.proposerName`，详情「提出人」直接展示；不参与负责人匹配、不通知；分析前 `analysisPiiMarkers` 会把该姓名加入掩码；占位串（如「（姓名已掩码）」）不入库。
5. **客户端**：`applyDraft` 默认只填空白字段（有内容时确认合并/覆盖）；用户编辑后撤销该字段的「AI 填充」标记；429/503 按错误码提示并显示 `Retry-After` 的等待时长；幂等键只在创建成功或显式放弃后轮换，409 提供「换新键重提」出口；提交带 `intakeOrigin` 与 `proposerName`；补齐标题/描述/型号/约束/链接的长度与格式校验、聊天框字数显示。
6. **5a.1 范围外**：多维表格同步（5b）、来源徽标/筛选/指标拆分/SOP（5c）、数据库迁移、`source_type` 新值、发版。

### 7.2 5a.1 目标环境验收与本轮修复（2026-11-18）

**验收结果**：release `7709402891559914800`（commit `9aaef82`，`finished`，`error_logs: []`）；完整记录见 `.scratch/prd26-5a/RESULTS-20261118.md`。

- A 5/5：5 段真实聊天（明确诉求、全类型 PII、口语化、长文多诉求、提出人+闲聊）全部抽取、创建，并走完 已分析 → 已推送。
- B/C/D/G/H/I/J PASS；K 由本地单测覆盖；F 目标环境 BLOCKED（妙搭客户端走平台 axios 封装，控制台构造不了同键重放），本地 `app.test` / `panels.test` 覆盖同键 200、异内容 409 与换新键出口。
- **E1 FAIL（P1）**：第 4 次/分钟抽取正确返回 429，但界面只显示「操作太频繁，请稍后再试。」，没有等待秒数。

**E1 根因**：`rq-sys-miaoda/client/src/rqsys/backendFetch.ts` 的 `toResponse()` 重建 `Response` 时只写 `content-type`，把 `Retry-After` 及其它响应头全部丢弃，`ApiError.retryAfterSeconds` 在妙搭端恒为 `null`；根仓 Web 用原生 fetch，本地单测因此为绿。修复：白名单透传响应头（至少 `retry-after`、`content-type`、`x-request-id`）或让 429 错误体直接带 `retryAfterSeconds`，并补客户端测试。影响面不止抽草稿：任何读取响应头的客户端逻辑在妙搭端都失效。
