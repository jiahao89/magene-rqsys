# MVP 通知收尾能力验证方案（待确认，2026-10-16）

## 工作流和要解决的问题

PRD revision 60 明确要求首次推送、实质变更、后续负责人分配/变更、AI 失败后重试成功的事件通知与去重。2026-10-15 收尾只读核对发现正式 Base 工作流 `wkfYO1EEYxJXbCaN` 为 disabled 且 steps=[]；原 POC 只证明负责人变更通知。因此不能将正式通知标为已交付。

## 方案选择

1. **推荐：应用识别事件，Base 自动化发送。** 主表增加四个系统元数据字段；不改变 PM 状态归属，不回读通知送达至 Web。复用现有推送版本与复合主键幂等。
2. 服务端通知 outbox + Base 负责人事件回调：可实现，但需要新的持久队列、回调与凭据，超过此次最小收尾成本；仅在推荐方案的目标能力验证失败时另行确认。
3. 只启用负责人通知：不能覆盖 PRD，本次不采用。

## 本次确认范围与停止条件

**本方案批准后先执行隔离 POC 能力验证，不把四个字段视为已经足够的最终通知实现。** 只向已批准 POC 表增加下面四个候选字段和测试自动化，消息只发贾浩。正式表、生产收件人和周计划保持原状。验证所需的合成事件由 CLI/UI 构造，不先改生产推送路径。

POC 表候选字段：`系统通知事件ID`（text）、`系统通知类型`（text）、`系统通知收件人`（多人员）、`系统负责人通知归并值`（单人员）。仅系统写入，不是 PM 字段，不进入模型，也不下发 Web。只有下述全部能力通过，才形成完整实现计划；任何一项不支持，记录事实并停止这条方案，不用时间窗口或布尔开关绕过去。

## 必须证明的目标能力

1. **不可变触发载荷**：E1、E2 连续修改同一行且 E1 延迟时，E1 仍使用 E1 的事件ID、内容与收件人，而不是当前单元格。若只能读取当前值，四字段主表方案失败，需改用追加事件表或服务端 outbox 的新设计。
2. **负责人合并和清空**：应用一次写入负责人及归并值不触发第二份负责人消息；人工分配非空负责人且不同于归并值时只通知新负责人。负责人清空时不发消息，但须将归并值清空。A→空→A 必须再次通知 A。
3. **迟到回写保护**：触发时 A、发送前/后改为 B，旧 A 执行不得把归并值回写为 A。须能以当前负责人仍等于触发负责人为前置条件，原子更新归并值；单纯“先查再写”不算通过。若原生平台不提供这种条件更新，则四字段方案失败。
4. **失败重试粒度**：验证原生执行记录是否支持对固定事件/固定收件人重试发送，以及部分收件人成功后不重复成功者。只看“有重试按钮”不算通过。失败不回滚业务推送，不在 Web 标示送达。
5. **同键重放静默**：只有新增事件ID或真实负责人变动才发送；重复写入同一事件ID、无变化源同步和没有新结果的分析重试均静默。必须使用实际消息与运行记录验证。

## 后续实现必须遵循的业务规则

- 通知条件分别计算，不使用丢弃收件人的单事件优先级。首次/实质变更的 PM Leader＋可解析提出人＋当前负责人，负责人变更的新负责人，AI 失败转成功的 PM Leader＋当前负责人；同次同时成立时合并原因和收件人并去重。只有人员映射变化、源版本未变时也能形成负责人事件。无变化静默不排除这种变化。
- 提出人只来自获准且已验证的源字段；当前最小 `field_map` 未建立提出人投影，所以记 `proposer_field_unavailable` 并跳过，不从标题、原始自定义字段或姓名猜测。未来获准映射后才解析。
- Base 有主键而应用无历史成功推送的旧行，视作应用首次成功推送；保留既有 PM 状态/确认值，不当成新建，也不无故重置为待处理。真正新建的行才初始化 PM状态=待处理；有证据的实质变更仍按 PRD 快照后重置。
- 后续实现必须在首次外部写之前持久化不可变推送/通知意图，固定完整写入投影、事件ID、原因及收件人。仅“每次重算确定性键”不满足重试合同。需要新增的持久化字段、仓储事务和跨进程单需求串行规则，在 POC 通过后纳入单独的完整实现设计与审查，不能直接复用当前会重读最新版的失败推送逻辑。
- 完整设计必须覆盖“Base 已写而应用未记成功”的恢复，以及旧推送不得在新推送之后覆盖字段。未实现这些保护之前，不把通知去重标为交付。
- PM Leader 初始为贾浩；不新增 RBAC。TB 无负责人仍可推送，并保留 Base 已人工分配负责人。当前负责人由既有 Base lookup 的人员字段取得；不把 PM 处理状态或通知送达回读至 Web。

## 执行和验收

1. 完成本能力验证方案审查和用户确认；先在 POC 配置候选字段/自动化与固定合成事件，所有测试收件人只限贾浩。模型不接收人员字段。
2. POC 验证新建、首次更新已有行、实质更新、同次负责人变化、后续人工分配/更换、AI 失败后重试成功、无变化/无新结果/同键重放静默及失败补发；需实际消息/执行记录，不以本地测试替代。
3. 新行初始化 PM状态=待处理；已有行不受首次推送初始化影响。来源字段按已批准字段映射加 TB 来源标记；不扩展全部自定义字段。
4. 正式来源先 source_only 回填，按本次原始接口ID核对；不分析、不推送、不通知。正式表无TB主键的旧行先保留，不能猜成测试数据删除。
