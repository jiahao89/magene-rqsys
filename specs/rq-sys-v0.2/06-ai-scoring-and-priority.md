# V02-S06 — AI 直接评分与 U/M/S/C v2 优先级

> 状态：target-verified（2026-10-28 目标验收通过；合成RQ-000343已验证并清理）。
> 基线：V0.2 本地 PRD（2026-10-27 修订，§4.2）；继承 MVP 与 V02-S02 不冲突的契约。
> 本文是增量约束，不表示相关功能已实现或已通过目标环境验收。

## Problem Statement

V0.2 现有的 U/M/S/C 规则 v1 只让 AI 给出“高/中/低/无法判断”，服务端把四维求和后分档。这个实现可解释、稳定，但不能表达原需求处理流程中的九项评分、α 修正和加权除以成本公式，也无法让 PM 修正单项分数。

2026-10-27 用户确认新的评分机制：

- AI 可以直接给九项输入打分，但必须同时给出评分依据、假设标记和说明；
- PM 可以修改任一单项分数和 α；
- 综合分和 P0–P3 由服务端按固定公式重算，不能由模型或人工直接改最终 P；
- 旧版 v1 优先级保留历史兼容，不静默回算。

## Solution

新增“评分 v2”作为版本化规则和需求级版本数据：

1. AI 输出九个输入项分数、α、每项依据/假设、总体评分说明、安全标记和评分置信度。
2. 服务端按固定公式计算综合分和 P0–P3；拒绝模型自报的 P，拒绝非法/无依据/越界评分。
3. PM 在详情查看 AI 建议和当前评分，修改单项或 α 后服务端重算，形成新版本并审计。
4. AI 重跑生成新建议但不覆盖人工确认值；用户显式“采用 AI 建议”后才切换当前值。
5. 评分明细只在 RQ-Sys Web/数据库；当前 P 沿用既有 Base 推送投影。人工改分不自动推送或通知。

## User Stories

1. 作为 PM，我希望 AI 直接给出 U/M/S/C 九项分数，以便不用把每个维度再手工换算成高低档。
2. 作为 PM，我希望每个分数都能看到原文依据或明确的假设说明，以便判断 AI 是否在编造。
3. 作为 PM，我希望看到 AI 的总体评分说明和置信度，以便知道这条评分能否直接采用。
4. 作为 PM，我希望看到固定公式和综合分，以便核对分数如何变成 P0–P3。
5. 作为 PM，我希望修改任一单项分数后系统自动重算，以便修正 AI 的误判。
6. 作为 PM，我希望修改 α 并填写理由，以便表达单渠道、多渠道或安全场景的证据强度。
7. 作为 PM，我希望 AI 建议和历史版本都保留，以便复盘为什么改过分。
8. 作为 PM，我希望 AI 重跑不要覆盖我已确认的评分，以便不被静默改优先级。
9. 作为 PM，我希望可以显式采用 AI 的最新建议，以便在需要时快速回到模型结果。
10. 作为维护者，我希望评分输入、公式、阈值和规则版本都固定，以便确定性回归和审计。
11. 作为维护者，我希望非法输出进入可重试失败，而不是写入伪精确分数。
12. 作为审查者，我希望安全相关评分触发复核提示，但不会自动改 P 或绕过公式。
13. 作为使用者，我希望评分失败不阻断需求创建、同步、负责人和 Base 推送，以便主流程可用。
14. 作为维护者，我希望旧版 v1 分析仍能读取和解释，以便升级不破坏历史。

## Implementation Decisions

### D1. 评分输入与公式

所有分数均为整数；α 为一位小数，范围 0.5–2.0。

| 维度 | 输入项 | 范围 | 说明 |
|---|---|---:|---|
| U | `pain` 痛点强度 | 1–5 | 1 几乎无感；3 明显不便；4 阻碍目标；5 涉及安全/不可逆后果 |
| U | `frequency` 发生频次 | 1–5 | 1 极少；3 每月；5 几乎每次/每天 |
| M | `sellingPoint` 卖点强度 | 1–3 | 1 无卖点；2 可作对比支撑；3 核心差异化 |
| M | `competitor` 竞品差异 | 1–3 | 1 未核实/无差异；2 持平；3 明显领先 |
| S | `roadmap` Roadmap 匹配 | 1–3 | 1 未规划/无证据；2 候选或中期；3 当前版本/战略重点 |
| S | `dependency` 战略依赖/杠杆 | 1–3 | 1 独立单点；2 复用现有平台；3 关键战略能力/跨产品协同 |
| C | `workload` 工作量 | 1–5 | 越高成本越大 |
| C | `technicalRisk` 技术风险 | 1–5 | 越高成本越大 |
| C | `resource` 资源占用 | 1–5 | 越高成本越大 |
| α | `alpha` 修正系数 | 0.5–2.0，步长 0.1 | 默认 0.8 单渠道、1.0 多渠道、1.5 已确认安全 |

计算：

```text
U = pain × frequency
M = sellingPoint × competitor
S = roadmap × dependency
C = max(workload, technicalRisk, resource)
U_adj = U × α
score = round2(U_adj × (1 + 0.6×M + 0.4×S) ÷ C)
```

P0–P3（唯一口径）：

| 综合分 | 优先级 |
|---:|---|
| ≥45 | P0 |
| 25–44.99 | P1 |
| 10–24.99 | P2 |
| <10 | P3 |

### D2. AI 输出契约

分析结果新增 `scoring` 对象：

```json
{
  "inputs": {
    "user": { "pain": 3, "frequency": 4 },
    "market": { "sellingPoint": 1, "competitor": 1 },
    "strategy": { "roadmap": 1, "dependency": 1 },
    "cost": { "workload": 3, "technicalRisk": 2, "resource": 2 }
  },
  "alpha": 0.8,
  "safetyFlag": false,
  "scoreConfidence": "中",
  "scoreConfidenceReason": "频次和竞品依据不足，已按假设估算",
  "basis": {
    "user.pain": { "reason": "用户描述循环选择难受，造成操作负担", "evidence": ["T1"], "assumption": false },
    "user.frequency": { "reason": "按夜间骑行每周 1–2 次估算", "evidence": [], "assumption": true },
    "market.sellingPoint": { "reason": "属交互细节，无对外卖点", "evidence": ["T1"], "assumption": false },
    "market.competitor": { "reason": "未核实竞品车灯交互", "evidence": [], "assumption": true },
    "strategy.roadmap": { "reason": "未引用实际规划版本", "evidence": [], "assumption": true },
    "strategy.dependency": { "reason": "未发现跨团队依赖", "evidence": [], "assumption": true },
    "cost.workload": { "reason": "多按钮页面和名称存储，初估 1–2 人月", "evidence": [], "assumption": true },
    "cost.technicalRisk": { "reason": "涉及多端同步，风险中等", "evidence": [], "assumption": true },
    "cost.resource": { "reason": "无额外硬件资源，按中等估", "evidence": [], "assumption": true }
  },
  "rationale": "交互优化价值明确，但单条反馈、竞品和规划证据不足，按 α=0.8 和成本 3 计算为 P3。",
  "proposedScore": 6.40
}
```

规则：

- 九项输入和 α 必须全部存在；缺项或越界拒绝整条评分。
- `basis` 必须覆盖九项。`assumption=false` 时必须至少有一个证据引用；`assumption=true` 时证据可为空，但必须写清估算假设。
- 证据只能引用本次分析输入中的原文片段；服务端沿用现有证据子串校验。
- `proposedScore` 仅用于说明，可与服务端计算不同；正式分以服务端为准，`priority` 不由模型给。
- 模型自报的 `priority` 字段必须忽略/拒绝；评分失败不能伪造默认 P。
- AI 评分输出与现有 `recommendations` 的兼容：v2 分析优先使用 `scoring`；缺少 `scoring` 的旧分析仍可读，按“未提供”展示。
- 评分输入中的文本（含假设说明）仍走 PII 掩码；不得把姓名、联系方式、ID 或附件内容发送给模型。

### D3. 服务端计算与校验

- 新增纯函数 `computeUmcScore(inputs, alpha)`，输出 `{ score, priority, breakdown }`；输入校验、范围、α 步长、C>0、有限数、四舍五入均在服务端。
- 计算器只支持本 Spec 的固定公式；不实现任意表达式脚本引擎，不提供阈值编辑 UI。
- 规则 v2 写入 `priority_rule_versions`：`formulaType: "umsc_weighted_v2"`、输入定义、α 默认、阈值、校准样例；发布 v2 时将 v1 置为 `retired`，但历史 `analysis_runs` 的 FK 保留。
- 旧 v1 分析仍按其规则版本解释；v2 只用于新分析或人工重跑，不自动回算历史。

### D4. 数据模型

新增 `requirement_score_versions`（名称实施时可调整，但语义固定）：

| 字段 | 说明 |
|---|---|
| `id` | UUID |
| `requirement_id` | 需求外键 |
| `version` | 需求内递增版本 |
| `status` | `ai_suggested` / `current` / `confirmed` / `superseded` |
| `source_version` | 需求来源版本 |
| `analysis_version` | 对应的分析版本 |
| `rule_version_id` | 评分规则版本 FK |
| `inputs` | 九项输入 + α 的完整快照 |
| `score` | 服务端计算综合分 |
| `priority` | 服务端计算 P0–P3 |
| `score_confidence` | 高/中/低与理由 |
| `safety_flag` | 安全复核标记 |
| `basis` / `rationale` | AI 依据、假设、总体说明 |
| `origin` | `ai` / `manual` / `ai_applied` |
| `actor_id` / `change_reason` | 人工操作者与理由 |
| `created_at` | 时间 |

`requirements` 增加当前评分版本指针（`current_score_version_id`，可空）。旧分析没有评分版本时保持空，不伪造。

### D5. API

- `GET /api/requirements/{id}` 的详情响应增加 `scoring`：
  - `current`：当前评分版本或 null；
  - `aiSuggestion`：最新 AI 建议或 null；
  - `history`：按版本倒序的只读列表；
  - `formula`：只读公式/阈值说明（可由服务端配置返回）。
- `PUT /api/requirements/{id}/scoring`：
  - body：`{ expectedVersion, inputs, alpha, safetyFlag?, reason }`；
  - 校验/重算/写确认版本/审计；`409` 版本冲突；`400` 输入非法；`404` 需求不存在。
- `POST /api/requirements/{id}/scoring/apply-ai`：
  - body：`{ expectedVersion, aiVersion, reason? }`；
  - 以指定 AI 建议生成确认版本；AI 建议必须属于该需求且仍有效；版本冲突 409。
- 权限：任何已登录租户用户可读写，actor 只取服务端可信身份；不新增应用角色矩阵。
- 审计：`scoring.suggested`、`scoring.updated`、`scoring.ai_applied`，保留 from/to 版本与安全摘要；不写敏感原文。
- OpenAPI 增量更新，schemas 与两仓契约一致。

### D6. UI

**信息架构（2026-10-28 修订）**

详情页顶部是摘要卡，之后是一个整合的“AI 评分与优先级”区域；不再保留独立的“AI 分析与建议”并列区块。

- **摘要卡**：最顶部是“返回需求池”；其下是标题/平台 ID、评分与优先级主视觉、负责人/流程状态/操作按钮。评分主视觉读取当前有效评分 `current`，显示综合分、P0–P3、置信度和版本；只有 AI 建议时标注“AI 建议（未成为当前）”；无评分时显示“暂无评分”，不伪造 0 分或 P。
- **AI 评分与优先级区域**：
  - 顶部：当前综合分、P、评分置信度、版本、来源（AI/人工/已采用 AI）、公式摘要和只读计算结果。
  - U/M/S/C 四张维度卡：显示合成值（U=pain×frequency，M=sellingPoint×competitor，S=roadmap×dependency，C=MAX(三项成本)）、计算式、AI 对该维度的建议/理由/证据/缺失标记。
  - 九项输入表：列包括“AI 建议”“当前值”“依据/假设”；α 单独一行；分组显示 U/M/S/C。
  - 编辑态：数字输入/步进器（整数范围；α 0.5–2.0 步长 0.1），修改理由必填；保存/取消。
  - 操作：保存、采用 AI 建议、查看历史；AI 建议与当前值不一致时显示差异提示。
  - 历史：版本、来源、操作者、时间、分数/P、修改项、理由；只读。
  - 次级内容：模块、类型、适用人群、整体置信度及其他 AI 判断；详细依据/推断/盲点仍在“查看依据与历史”折叠区。
  - **适用人群**：放在该区域；AI 建议使用浅色/虚线建议标签，PM 选项使用独立选择标签，保存按钮独立为主按钮；未确认时默认选中首个 AI 建议作为草稿，显式保存后才生效（见 PRD §4.4）。
- 状态：加载中、无评分（可手动填/重新分析）、评分失败（重试/手动填）、版本冲突（刷新重试）、规则未发布（待校准）。
- 不编辑公式、阈值和最终 P；不把评分输入当作可绕过主流程的门槛。
- 移动端/窄屏保持可读；评分摘要卡与维度卡纵向排列，九项输入表可横向滚动；键盘可操作。
### D7. 生命周期与重跑

- AI 分析成功且评分合法：
  - 无当前版本 → 创建 `current`（origin=ai）；
  - 有当前版本 → 创建 `ai_suggested`，保留当前，详情显示差异。
- PM 保存 → 新 `confirmed` 版本；旧 current 变 `superseded`；当前指针更新；审计。
- PM 采用 AI → `confirmed`（origin=ai_applied），需记录显式操作。
- AI 重跑/需求编辑不覆盖当前人工值；旧评分版本只读。
- 旧分析没有 scoring → 详情显示“未提供评分”，不自动补分。

### D8. 与主流程、Base、Beta 的边界

- 评分 v2 是主分析的一部分；当前 P 用于既有 Base “AI优先级建议”投影。
- 人工改分/采用 AI 不自动推 Base、不重置 PM 状态、不发通知；需要更新 Base 时走既有手动推送或后续编辑流程。
- 评分失败/缺失不阻断需求创建、同步、负责人分配、Base 推送。
- RICE/Kano 只读或手动 Beta，不参与评分 v2；Kano 无合格样本时保持“未评”。

### D9. 安全、异常与不可用

- 安全标记触发复核提示，不自动改 P；复核意见进入审计/历史。
- 非法输入、无依据、证据不存在、α 越界、C≤0/非有限数 → 拒绝评分，保留上一有效版本，错误可见。
- AI 超时、限流、非法 JSON、规则未发布 → 评分失败可重试；主流程不受阻。
- 证据/假设校验与 PII 掩码沿用现有分析适配器；不在日志打印原始证据/个人信息。

## Testing Decisions

- 纯函数/边界：九项范围、α 步长、C 最大值、四舍五入、P 阈值边界（45/25/10）、非法输入。
- AI 契约：合法输出、缺项、越界、无依据、假设无说明、证据不在原文、自报 priority 被拒绝；旧分析无 scoring 兼容。
- 仓储/迁移：评分版本唯一当前、状态迁移、审计、并发 409、当前指针、回滚/重试。
- API：GET 详情、PUT 编辑、apply-ai、权限、404/400/409、敏感信息不泄漏。
- UI：加载/空/失败/冲突、编辑单值/α、理由必填、预览、采用 AI、历史、AI/当前差异；摘要卡评分/P、返回顶部、评分-AI 单一整合区、U/M/S/C 维度卡、人群默认选中与视觉分层、移动端/深色。
- 目标：受控合成需求验证 AI 证据/假设、公式、人工编辑、版本/审计、Base/P 投影、失败隔离和清理；不把本地结果当目标证据。

## Out of Scope

- 让模型直接决定最终 P0–P3，或让用户直接编辑 P/公式/阈值。
- 任意表达式脚本引擎、用户自定义公式、评分规则管理 UI。
- 自动回算历史分析、自动重推 Base 或通知。
- Kano 真实样本/统计比例；RICE 参与主评分。
- 把完整评分明细新增到 Base 字段。
